An annotated starting point for an effort review

Copy the visual structure, replace the examples, and retain only the sections that help a reviewer make the next decision. This reference explains when its header elements apply and when they do not.

Decision review Issue #148 scope: repo-wide

Purpose and boundary

Use this as an annotated template, not a second policy source

One review document per active effort. The document may begin before a ticket exists, grow through planning and verification, and conclude with handoff. GitHub remains the source of truth for issue status, assignment, priority, dependencies, and follow-on work.

The visual baseline is .ai/reports/2026-08-17-bountiful-quests-prototype.html: a masthead, restrained accent color, readable technical measure, responsive tables, evidence panels, and self-contained assets. Do not copy every component merely because it is available.

Header guidance

Use the header to orient the reviewer

ElementUse it forOmit it when
.kickerStable context: effort kind, issue link or identifier, and authored date. The information is repeated by the title or would require frequent maintenance.
h1The question, proposed change, or outcome a reader is reviewing. Never; every review document needs a descriptive title.
.standfirstA two- to four-sentence plain-language framing of the decision or evidence request. Only for a trivially small document where it would merely repeat the title.
.statusbarReview context: requested feedback, a ticket link if one exists, and static scope. It would contain only volatile implementation or tracker state.

Metadata boxes

Chips say how to review, not how work is progressing

Allowed: review mode

Use one accented chip such as proposal review, decision review, implementation review, or handoff review. It tells the reader what feedback is useful now. It is local document state, not backlog state.

Allowed: stable identifiers

Use neutral chips for a linked issue number once it exists and for stable scope such as mod:AutoCollectLoot or scope: repo-wide. Before issue creation, omit the issue chip entirely; do not show ticket pending.

Keep evidence in evidence

Put build results, test counts, candidate readiness, changed-file inventories, and CI outcomes in their detailed verification section. The submission verifier’s generated section remains the authoritative candidate record.

Never use chips for GitHub work state. Do not repeat open, closed, priority, assignee, blockers, milestone, or “nothing committed.” Those values drift and belong to the issue or generated candidate evidence. If an approval must be visible, record the approved decision in its detailed section with a link to the approving comment or ticket.

Body composition

Choose sections by the reviewer’s decision

  • Start with a linked, impact-prioritized decision table when a review asks for choices.
  • Use a separate naming table for names a developer must type, configure, or search for.
  • Use a diagram when topology, temporal order, or branching is load-bearing; otherwise prefer prose, code, or a table.
  • End with verification and handoff evidence when the document reaches implementation review.

Diagram example and guidance

Use a small, self-contained SVG when the shape carries meaning

RuleWhy it matters
Use viewBox, CSS classes, and theme variables. The diagram scales with the page and retains contrast in both color schemes.
Give each node label its own class; use explicit tspan lines for multi-word text. A generic svg text rule can override label contrast, and a one-line label can overflow its node.
Keep connectors out of label space. A sequence line crossing text makes both the relationship and the label harder to read.
Give each marker a document-unique ID, such as loot-flow-arrow. SVG IDs are global within the HTML document; repeated arrow IDs can redirect connectors.
Use role="img", a concise aria-label, and a visible caption. The relationship remains available to screen readers, search, and readers who prefer prose.
Open the copied document directly in a browser before handoff. Source inspection cannot catch layout overflow, contrast regressions, or malformed surrounding HTML.
Use the smallest useful diagram. Do not add SVG to decorate a simple list, comparison, or one-step action. A table or short paragraph is easier to maintain when it explains the relationship just as clearly.

Handoff evidence

Keep the verified candidate inside the review document

The submission-candidate section is the only file manifest for the effort. It is generated by verify-submission-candidate; the reviewer’s plan, analysis, and decisions remain elsewhere in this same document.

Template author

Keep one marker-bounded placeholder near the end of the copied review document. Include the review document itself in the candidate’s explicit file list.

Verifier

Replace only the marker-bounded block after the scratch candidate passes. Render the same block in the scratch overlay before validation, then write those bytes to the real document after success.

Reviewer

Read the generated base, commands, outcomes, and paths as the exact handoff contract. If any selected file changes, require a new verifier run instead of editing the manifest.

Do not maintain a parallel inventory. The generated block answers “what may I submit?” It does not replace the document’s explanation of why the change exists or the GitHub issue’s work state.

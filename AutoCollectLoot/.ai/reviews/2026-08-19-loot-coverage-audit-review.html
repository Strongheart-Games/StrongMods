AutoCollectLoot support diagnostics19 Aug 2026

Explain every enemy loot drop after startup

Issue #147 adds a read-only startup audit so a downstream user can send one log and show which enemy loot-drop containers AutoCollectLoot can replace, which it cannot, and why.

Decision review Issue #147 mod: AutoCollectLoot

Support outcome

The runtime knows what can drop; the patched XML explains why generation missed it

The existing item generator selects XML declarations. Actual deaths use the post-load EntityClass.lootDrops graph, whose values already include inheritance and every earlier mod. A useful audit must join those two views: runtime data defines the candidate set, while final patched XML supplies the declaration provenance needed to distinguish missing data, inherited data, and unsupported inheritance depth.

Terminology correction. The issue asks for an “eligible” count, but an excluded drop bag cannot be both ineligible and an omitted eligible target. The log should use candidates, configured, and omitted: three names that form one unambiguous partition.

Mechanics

Capture provenance early; evaluate coverage late

Runtime candidate universe

After the readiness gate, enumerate EntityClass.list.Dict.Values, keep classes with bIsEnemyEntity, and collect every valid target referenced by their resolved lootDrops. De-duplicate targets by entity-class name while preserving a reverse mapping from each target to every enemy class that references it. This mirrors the data path used by EntityClass.LootDropPick and naturally includes earlier mods and inherited enemy definitions.

Final XML snapshot and stability-gated startup timing

A Harmony postfix on EntityClassesFromXml.LoadMain(XmlFile) captures each entity name, @extends link, and directly declared Class, Mesh, and LootList values from the already-patched file. It retains compact provenance, not the XDocument.

Static inspection establishes that base-game entity and item loading completes before GameStartDone, but the event invokes mod handlers synchronously and cannot prove downstream post-processing is finished. The server-side handler therefore arms the audit instead of running it. GameUpdate samples at most every 250 ms; the complete candidate/substitute input must remain unchanged for five seconds. Any change restarts that quiet period.

If prerequisites are missing or the input never settles within 30 seconds, emit one inconclusive warning with readiness evidence and no per-container claims. A provisional omission can become false moments later, so presentation alone cannot make an unsettled result trustworthy. Clients do not sample or log. A shutdown or later game start resets the one-shot coordinator.

One omitted container, then every affected enemy

Sort omitted loot-container classes by exact identifier and emit at most one container group for each. Follow it with one bullet per distinct affected enemy class under Affected Enemies:, also sorted by exact identifier. The admin-facing heading stays concise; every bullet remains an exact XML entity-class identifier, not a localized display name. An enemy that references two omitted containers appears under both; the affected enemy count in the summary counts that enemy once across the report. Enemies whose containers are all configured are not listed.

The omitted container’s reasons= field contains one or more of:

  • excluded-drop-bag-policy — effective loot list is cntDropBag.
  • missing-required-data — no effective Mesh or LootList.
  • inherited-required-data — required data exists only on an ancestor and the generator cannot safely consume it.
  • unsupported-inheritance-depth — the target is more than one link below a direct EntityLootContainer declaration.
  • unsupported-drop-entity-class — no declaration chain identifies the target as an EntityLootContainer.
  • missing-substitute-item — the XML declaration should match the generator, but no mapped item exists at runtime.
  • invalid-substitute-item — a mapped item exists but its action class or loot list disagrees with the target.

When more than one reason applies, emit tokens in the diagnostic order shown above. Parenthesized evidence uses stable names such as depth=2 and properties=Mesh,LootList.

Configured means behaviorally usable

A candidate counts as configured only when the item map has one substitute whose AutoLootSubstituteFor targets that class, whose Action0/Class is OpenLootBundle, and whose Action0/LootList equals the target’s effective runtime loot list. The audit reuses the same item-indexing logic as collection so diagnostics and behavior cannot drift.

The audit observes; it does not repair

No audit path writes XML, creates substitute items, changes the collection map, or treats deeper descendants as supported. The existing one-level generator remains the product contract. A future behavior change may consume these diagnostics, but #147 only makes omissions legible.

Always-on, once, server-side

V1 adds no configuration gate. The summary is one Log.Out line; intentional policy exclusions are informational, while capability or configuration omissions use Log.Warning. Running once avoids steady-state noise, and always-on evidence supports “send me the log” without asking users to reproduce with a diagnostic switch. Add a gate only if real-world volume shows that this bounded policy is too noisy.

Human readability is the primary interface. Use two spaces per hierarchy level after the repeated [AutoCollectLoot] prefix. Reasons: is always a list, even when it has one entry; stable kebab-case tokens remain grep-friendly, while changing evidence uses parenthesized key=value fields. Emit each omitted-container group as one multiline call to reduce interleaving, with no blank log records between groups. Use Log.Out only when every reason in a group is an intentional policy exclusion; otherwise use Log.Warning.

Implementation plan

  1. Add LootCoverageAudit with a compact declaration snapshot, pure report generation, and the game-state/logging adapter.
  2. Register final-XML capture plus server-side GameStartDone, GameUpdate, and shutdown handlers from ModApi.
  3. Add an injected clock/snapshot seam: sample at most every 250 ms, require five stable seconds, and stop inconclusively after 30 seconds.
  4. Reuse or deepen LootItems indexing so collection and audit share substitute interpretation.
  5. Preserve the reverse enemy-to-container mapping and log only enemies affected by omitted containers.
  6. Add synthetic tests covering timing, every reason, multiple reasons, grouping, de-duplication, deterministic order, and summary arithmetic.
  7. Update README.md and bump ModInfo.xml to 0.2.0.

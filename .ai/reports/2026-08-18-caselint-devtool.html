Research

The runtime feature today, and what its three bugs say

StrongMods ships CaseSensitiveFilesystem (StrongMods/CaseSensitiveFilesystem.cs): a Harmony transpiler that replaces File.Exists, Directory.Exists, SdFile.Exists and SdDirectory.Exists with its own case-checking Exists inside four game methods (Localization.LoadPatchDictionaries, ModManager.LoadUiAtlases, ModManager.LoadLocalizations, XmlPatchMethods.Include — lines 284–314), plus ValidateModInfos (line 236), which unloads any mod whose ModInfo.xml fails the case-sensitive probe. The whole feature is gated on Config.CaseSensitiveFilesystemEnabled (StrongMods/Config.cs:10), an auto-probe of whether the host filesystem ignores case.

There is also a fifth call site the issues do not mention: StrongMods/BreadthFirstXmlPatcher.cs:106 calls CaseSensitiveFilesystem.Exists directly for every mod-config probe. That one turned out to matter — see the finding below.

Finding

The gate does not gate the fifth call site

New defect, found this session. When Config.CaseSensitiveFilesystemEnabled is false — i.e. on every production Linux server, which is the state #90's fix exists to guarantee — CaseSensitiveFilesystem.Init() is never called (StrongMods/ModApi.cs:55–64 returns before it), so s_anchors stays the empty array it was initialized to (CaseSensitiveFilesystem.cs:20). But BreadthFirstXmlPatcher is gated separately and is always on (Config.cs:7, ModApi.cs:25–31), and its phase-2 loop probes every mod's patch file through CaseSensitiveFilesystem.Exists unconditionally (BreadthFirstXmlPatcher.cs:105–108). With no anchors, AnchorFor falls back to Path.GetPathRoot (lines 165–175) — so every probe walks segment-by-segment from the filesystem root, enumerating every ancestor directory (lines 109–158).

Consequences on a production Linux server, per boot: one root-anchored directory walk for every mod × every eligible vanilla XML file (order: ~25 mods × dozens of files — roughly a thousand walks; structural claim, not measured), each enumerating every ancestor from / down. On a multi-tenant host that is exactly the I/O pattern #89 was about — now non-fatal (the catch degrades it to a warning per unlistable directory), but the feature the gate says is off is still running its most expensive path, and its Log.Error mismatch messages (lines 147–151) can still fire in production. The gate is off in name only for this call site.

Fix direction (either suffices): have Exists fast-path to File.Exists(path) || Directory.Exists(path) when the feature never initialized, or route the breadth-first patcher's probe through the gate so an off state uses SdFile.Exists directly. Proposed as a ticket below.

The tool

caselint.cs — six rules, disk is the authority

StrongDev/.ai/tools/caselint.cs (written by the earlier attempt, verified and run this session; usage: dotnet run StrongDev/.ai/tools/caselint.cs, -- --selftest, -- <ModName>). Two design rules keep it honest:

  • Disk is the authority. A reference is flagged only when a target exists under the mod with a different spelling — a case-insensitive hit that is not an ordinal match. A reference matching nothing at all is a broken-reference problem (#50 gap S3), not a casing problem, and is not reported — except <include>, where the miss is certain and cheap to see (reported as a warning).
  • Host-independent by construction. The resolver enumerates real directory entries and compares names itself (Resolve, lines 252–281), never asking the host filesystem whether a spelling resolves — so it answers identically on Windows and Linux. (Design property; an actual Linux run remains unverified.)

Exit code: 1 when any error exists, 0 otherwise — CI-usable as is. Vanilla baseline resolves from packages/ automatically; SDTD_TREE overrides.

Recommendation

The #95 answer: lint is the guarantee, runtime is the opt-in residue

What a dev-time tool covers

Everything the runtime feature checks, plus more, at zero server cost: all six rule classes above run against every mod on every invocation — including files a given boot never touches (the runtime check only sees paths the four patched methods happen to probe). It reports at the moment the author can act, names the correct spelling, and never reads a directory outside the repo. #89, #90 and #91 are all structurally impossible for it: there is no server, no gate, and no BCL substitution.

What residue genuinely needs runtime support

  • Outside modders. StrongMods is published for modders outside this repo (CONTEXT.md); a lint living here never sees their mods. This is #95's stated constraint and the main argument against full retirement.
  • Other authors' mods co-installed on a live server, which no repo lint can enumerate.
  • Paths composed at runtime from data the lint cannot see (the code-literal rule catches only literal fragments).

Worth restating from #95's established facts: the game itself compares its two mod roots case-insensitively (GameIO.PathsEquals(…, ignoreCase: true)), so the runtime substitution enforces a stricter rule than the host does.

Recommendation (for the human to weigh on #95 — not enacted here)

  1. Adopt the lint as the guarantee for this repo — graduate caselint.cs from its .ai/tools prototype home into repo tooling (ticket below; home is an open decision — a StrongDev tool run in CI, or a Tests convention test in the shape of #94).
  2. Demote the runtime feature to opt-in, default off. Config.cs already has the per-feature toggle shape. A Windows mod author testing locally opts in; a server operator gets nothing from it and no longer pays for it. Keeping the current auto-gate instead (now that #90's fix landed) is defensible but leaves production one probe-bug away from re-running the walk — #90 is the precedent.
  3. Fix the ungated fifth call site regardless — it bites today, with the feature nominally off, on every production boot. This is independent of whatever #95 decides.
  4. Do not retire outright yet. The outside-modder audience is real and the opt-in shape keeps the diagnostic reachable for them at near-zero cost to everyone else. Retirement becomes reasonable only if the opt-in is judged not worth its maintenance against #91's still-open conflation.

Trade-off stated plainly: the lint covers this repo completely and outside modders not at all; the runtime feature covers whoever runs it and costs whoever forgets it is running. Opt-in runtime + repo lint is the only combination where each cost lands on the party who chose it.

Remains

What remains

  • Graduation decision — where caselint permanently lives (StrongDev tool + CI step vs a Tests convention test; Tests/ was off-limits to this effort by mandate), and whether xml-path-ref/code-literal warnings should gate.
  • Linux execution of the tool is unverified — the resolver is host-independent by design, but no run happened on a case-sensitive filesystem.
  • #91 is still unfixed — the file/directory conflation survives in current source and is untouched by this effort.
  • Not covered by the lint: asset names inside .unity3d bundles (a different hazard class — bundle lookup, not filesystem), paths appearing in Localization.csv values, and runtime-composed paths.
  • ValidateModInfos unload-on-false — whether unloading a mod over a casing probe should survive in any runtime shape is part of the #95 weighing, not decided here.
  • Issue writes were out of scope (gh read-only): the tickets below are proposals, and the recommendation has not been posted to #95.

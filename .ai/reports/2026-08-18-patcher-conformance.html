Patcher Conformance

The breadth-first patcher's headline guarantee — a mod sees every earlier mod's XML edits and never a later mod's — is now asserted above the cache, with synthetic multi-mod fixtures driving the real XmlPatcher.PatchXml and the real cache. The config replay also gained post-patch value assertions: six real StrongholdTweaks balance edits are now checked for the value they were written to set, via a reusable row table any mod can join. The part that stays out of headless reach — the coroutine that runs the loop in-game — is mapped line-by-line below, with the seam that would close it.

What was attempted

Two related test-harness extensions from the #50 tool-gap seed (.ai/test-idea-tool-gap-seed.md):

  • F1 — the ordering seam. Build synthetic multi-mod fixtures that drive the real patcher and prove: (1) a later mod's <foreach> sees an earlier mod's patched XML; (2) an earlier mod does not see a later mod's patches; (3) one mod's malformed patch file does not abort other mods' patches; (4) eligibility filters. Where the path is unreachable headlessly, document precisely where it stops and specify the missing seam.
  • S5 — value assertions. Today Tests\Patcher\PatchApplicationTests.cs replays every mod's Config and asserts only clean application. Add post-patch value assertions for real StrongholdTweaks balance edits, as a reusable (xpath → expected) table.

Findings

1 — The ordering guarantee holds, proven with the real patcher primitives

Tests\Patcher\BreadthFirstOrderingTests.cs (new) enacts phase 2's per-(mod, file) sequence with two synthetic mods: ItemAppender appends an item to items.xml; BlockGenerator generates one block per item by reading items.xml cross-file (<foreach source="items" …>). The same pair runs twice, in opposite load orders:

  • A_later_mods_foreach_sees_an_earlier_mods_patch_to_another_file — with ItemAppender first, BlockGenerator's foreach produces a block for the appended item. Earlier mods' work is visible, regardless of which file it landed in.
  • An_earlier_mods_foreach_does_not_see_a_later_mods_patch — order swapped: the foreach produces a block only for vanilla's item, none for the item appended after it, and the later patch itself still landed in items.xml. Later mods are invisible to earlier ones.

What is real in these runs: the game's XmlPatcher.PatchXml (the same method phase 2 invokes, per patch file), the actual s_patchedFiles dictionary inside the loaded StrongMods assembly, in-place mutation of cached documents, and foreach's source= resolution through BreadthFirstXmlPatcher.TryGetPatchedFile. What is enacted by the test rather than executed from shipped code: the loop nesting itself (mod-major order, file order) and the per-application try/catch — mirrored from lines 89–125, following the precedent of Tests\Fixtures\PatchPipeline.cs, which already mirrors phases 1–2 the same way for the replay suite. The distinction is spelled out in the test class doc-comment.

2 — Failure isolation: verified first, then pinned

The task required verifying what actually happens before asserting. Observed on V3.1.0-b14 (the default tree host, where all engine-conformance tests run):

  • Command-level failures do not abort the file or later mods. A_mods_failing_commands_do_not_abort_its_later_commands_or_later_mods: a patch file carrying a no-match <set>, an unknown <frobnicate> command, and a valid <append> still lands the append; the next mod's patch applies cleanly; the failures are logged as warnings/errors, not swallowed.
  • A malformed patch file throws at read time, before touching the target. A_malformed_patch_file_throws_at_read_time_and_leaves_the_target_untouched: probed 2026-08-18 — the game's XmlFile constructor throws System.Xml.XmlException at parse time (surfaced through the reflection harness as TargetInvocationException). The target document is left untouched, so a malformed file can never half-patch anything. This is the contract phase 2's shipped try/catch (lines 110–118) relies on to log-and-continue per (mod, file) — the catch itself lives in the unreachable coroutine, so cross-mod resilience is asserted under the test's mirror of that catch, not the shipped one. Making the shipped catch directly testable is the seam below.

Decisions and trade-offs

  • Enact phase 2 rather than force the coroutine. Driving LoadAllXmlsBreadthFirstCo by reflection dies at WorldStaticData.xmlsToLoad (finding 3, first row) — and the repo had already established that fact when building EntryPoints.cs, so no time was spent re-proving it by execution. The trade-off is honest and recorded in every affected test: ordering and resilience are proven over the real primitives, while the loop shape is mirrored. The seam spec is the path to closing that residue.
  • The test helper mirrors phase 2's try/catch. Precedent: Tests\Fixtures\PatchPipeline.cs already wraps each application the same way (lines 113–117) for the replay suite. Without the mirror, assertion (3) could not be expressed at all; with it, the assertion verifies the design holds given the catch — the catch's existence in shipped code remains source-verified only (lines 110–118).
  • Value rows assert "every match equals", not "exactly one match". setattribute-style edits can legitimately hit several nodes; requiring all matches to carry the expected value catches both a missed set and a partial one. Trade-off: a second same-named node that coincidentally carries the right value would hide — acceptable for balance edits whose xpaths are already entity-scoped.
  • Ordering tests run on the default tree only. They exercise StrongMods' engine semantics against synthetic XML, not per-mod compatibility, so one tree suffices — the same standing decision the Foreach and PatcherCache suites follow (PatcherHost.Instance doc, .ai/testing-declared-versions.md §3c). Value assertions, being per-mod content claims, run per declared label.
  • Refactor instead of a second replay. Sharing the memoized pipeline (PipelineRuns) touches an existing test file, but the alternative — each class replaying every mod's Config against full vanilla per label — doubles the suite's most expensive fixture for no assertion gained.
  • items.xml's Stacknumber edit was deliberately not made a row. StrongholdTweaks\Config\items.xml:85 sets every Stacknumber > 1 to 65000 across the whole document — hundreds of matches whose expected set depends on which items other patches append. A row for it needs either a per-item scope or a count-shaped assertion; left for the table's next joiner.

What remains

  • The coroutine loop itself is still untested — eligibility filters (prologue lines 47–70), the GameConfigMod skip, the shipped try/catch, and the mods×files nesting execute only in-game until the seam lands. The seam spec in finding 3 is the concrete next step; the tests to write against it are already sketched there.
  • The value table has one tenant. StrongholdTweaks' six rows seed it; the pattern is built for other mods to join (any (Mod, EntryPoint, XPath, Expected) row works, version-pinning respected automatically). Candidates from the seed doc: StrongholdTweaks' remaining balance domains, ProgressiveBiomes' spawning edits.
  • Cross-file ordering under <include> was not exercised — the fixtures patch entry-point files directly. Follow-on once the seam exists, since include resolution happens inside the game's patch-file read.

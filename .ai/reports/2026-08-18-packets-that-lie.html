What a well-behaved client never sends

The server already knows which authenticated client sent every packet. An invariant asks one question of each one: does what this packet claims agree with what the server already knows? Nineteen of them now run, and log every answer of no.

build clean 403/403 tests 22/22 logic checks never run on a server detection only

Handling

Read this first

This is defensive work, written as detection rules rather than attack recipes. It stays clear of the vanilla-engine findings that #74 routes to private, pre-disclosure handling. Where a rule exists because a vanilla check is missing, it says which check is missing and stops there. None of it belongs in public issue text.

The surface

124 packets the server accepts from a client

A scan of all 190 NetPackage classes in V3.1.0-b14. The receive gate only rejects a packet whose declared direction equals the disallowed one, and Both is the base-class default — so a packet that is conceptually server-to-client but never overrode its direction still arrives from a client.

The gap, stated precisely

91 of those 124 are reachable because nobody overrode a default, not because anybody decided they should be.

This is not a list of 124 bugs. Most are harmless, or guarded further down the call path. It is a list of places where the server has enough information to check and does not — which is exactly where a detection rule pays for itself.

The question

Every invariant asks the same thing

NetPackageManager.ParsePackage sets Sender from the authenticated transport before the packet is even read. So every handler already holds two versions of the truth: the one the packet asserts, and the one the connection proves.

The catalogue

Seven families, five of them built

Ranked by detection value against cost and false-positive risk

A — Sender binding The entity a packet names is the sender's own 7none known

E — Rate A packet arrives no faster than a real client sends it 0needs observed defaults
C — Plausibility A claim agrees with where the server believes things are 0highest — lag is normal

C and E are catalogued and deliberately not built. Both need thresholds that come from a real server's numbers, and shipping a guessed threshold as a detection rule produces noise that teaches an operator to ignore the log.

Family A

The cheapest rules are the best ones

One integer comparison. No world lookup, no threshold. A real client only ever names itself in these packets, and vanilla already ships the helper — these are the packages that do not call it.

Why chat is on this list

GameManager.ChatMessageServer re-derives the display name from the client-supplied sender entity id before broadcasting. The server's own log line records the real platform id. So the log stays honest while the chat window does not — and msgSender is client-supplied too, with Server among its legal values.

Family B

Your example, generalised

You asked whether the no-PvP rule could extend past players to their vehicles, drones and robots. It can, and it collapses to one rule, because the game spreads ownership across four mechanisms that a single resolver can read together.

How ownership resolves
MechanismCovers
ILockable.GetOwner() / IsUserAllowed()vehicles, drones
Entity.belongsPlayerIdturrets, drones, anything spawned for a player
EntityTurret.OwnerIDturrets re-bound after a reload
attachment — GetAttached(slot)anyone riding, driver or passenger

With that in place, "damaged another player" and "buffed another player's drone" become the same check, and the family covers four packages: damage, buff, velocity, and retargeting AI.

Two false positives, already shipping

The 0.0.1 damage check accused two kinds of innocent player.

Vehicle passengers. It allowed only the owner to damage an unoccupied vehicle, and checked attachment before that — but a passenger the owner let in is not necessarily on the allowed-user list. Attachment is now checked first, for any seat.

Crossplay players. It compared the owner against PlatformId alone. ClientInfo.InternalId is CrossplatformId ?? PlatformId, so a crossplay player acting on their own vehicle read as a stranger. Both ids are compared now.

The family is inert unless PlayerKillingMode is NoKilling. Any other killing mode allows player harm by definition, and pretending otherwise would make the whole family noise.

What it looks like

One line per violation, and never more than three a minute

WRN [AuthZ] violation pve.buff
  | client=Bob/Steam_76561198...
  | package=NetPackageAddRemoveBuff
  | expected=under NoKilling, a client does not buff or debuff another player or an entity they own
  | observed=tried to buff or debuff EntityDrone owned by Steam_7656... (entity 4210)

A client that spoofs one entity id spoofs it every frame, so an unthrottled log turns one misbehaving player into a full disk. Lines are capped at three per client per rule per minute; the window closes with a count of what it swallowed. Every failure is still counted.

Modes, per rule

off — not checked, and the package is not even patched.
log — checked, logged, let through. Every rule ships here.
block — checked, logged, dropped.

Why nothing blocks

A rule that has never run against real traffic has no business dropping its packets. The number that decides promotion is the false-positive rate on honest traffic, and nobody has that number yet.

The seam

Patch what is enabled, not what exists

ConnectionManager.ProcessPackages is the single point every inbound packet passes, but it is a loop over a list it fills itself — a prefix cannot see the packets and a transpiler over it would be brittle.

The engine instead uses Harmony's multi-target form: TargetMethods() returns the declared ProcessPackage of every package type with an enabled rule. Four enabled rules patch four methods, not 124. Turning everything off patches nothing at all.

Each target resolves to the type that actually declares the override, since several packages inherit it, and dispatch walks the runtime type's bases — so a base-class patch never fires twice for one packet.

Evidence

What is verified, and what is not

Verified off-game

  • Builds clean, no warnings.
  • 403 of 403 repo tests pass. The suite resolves TargetMethods() against both V3.1.0-b14 and V3.0.1-b4, so all 19 named packages exist and their handlers resolve in both builds.
  • 22 checks over the game-free pieces: settings parsing and fallback, id uniqueness and shape, every invariant class actually registered, and the shipped settings template naming exactly the set the sources declare.

Not verified

  • That any rule ever fires — on honest traffic or dishonest.
  • The false-positive rate on honest traffic. This is the number that gates promotion to block mode, and it is the reason nothing ships there.
  • The per-packet cost of the prefix on a busy server.
  • The ownership resolver against real drones and turrets. It is read from the entity classes, not observed.
  • That the settings file round-trips through the save folder.

Over to you

Three decisions

  • Run it on Hades in log mode. Everything downstream — which rules can block, what the rate ceilings are, what a plausible reach threshold looks like — needs a week of real logs. Nothing else unblocks families C and E.
  • The harness belongs in the test suite. A parallel session has landed Tests/Fixtures/ModLogicHost.cs, which executes mod logic headlessly against the game assemblies. That is the right home for these checks and for real ownership tests. I did not build on it because it is still uncommitted.
  • Editor traffic. Two rules fire on any world-editor packet reaching a live server. If you ever edit Hades live, they need to be off — worth deciding now rather than from a log full of your own activity.

Nothing is committed. The working tree also still carries last night's BountifulQuests work.

Problem

Plans and specs under .ai/ are often the owner’s primary review surface. The existing convention calls them Markdown while a newer handoff flow writes submission evidence into an HTML report. That splits one effort’s design, evidence, and handoff across documents with overlapping review responsibility.

The review surface

Canonical review document

An effort has one HTML review document, created when planning begins and expanded as decisions, implementation evidence, and handoff information become available. It is self-contained so it opens directly from disk and remains usable in an archived checkout.

What changes, and what does not

Adoption boundary

New and actively revised effort artifacts live under .ai/reviews/YYYY-MM-DD-<effort>-review.html. The date makes contemporaneous review documents sortable; the effort slug tells a reader what is being reviewed without opening the file.

Markdown remains the format for AGENTS.md, skills, ADRs, READMEs, and shipped technical references. Those are source-like or agent-facing documents; changing them would require separate evidence that HTML improves their authoring and maintenance, not just their rendered reading experience.

Migration risk. Bulk conversion obscures history, produces broad noisy diffs, and consumes review time without improving the current effort. Historical documents remain as they are; a document moves only when its owning effort actively revises it.

A test for visual explanation

Diagram gate

A diagram is required when understanding depends on topology (who connects to whom), branching, or temporal order. It is optional when a short paragraph, code block, or table is more precise. Diagrams must be embedded SVG or HTML/CSS, accessible without JavaScript or network access, and accompanied by text that states the claim for search and accessibility.

One vocabulary

Submission-verifier contract

One review document follows an effort. A submission candidate is the exact file set a human may submit; an effort can have more than one verification run without creating more review documents. The tool-generated verified candidate manifest is the receipt inside the review document, not a second document and not the input to a future run.

The verifier continues to receive explicit candidate files for now. Reading a prior generated manifest would risk validating a stale list. A future candidate declaration inside the review document could become the input only if its convenience justifies another maintained section; that is deliberately deferred. Once #145 is submitted independently, #148 will rename the unshipped command-line parameter --report to --review, its marker wording, and its skill language. This is a naming correction, not an expansion into a general documentation-authoring skill.

One Core, Five Copies

The grounded extraction inventory for StrongCore: what is actually duplicated across the repo's 18 code mods, where each copy lives, what deserves to move, and how the pieces should travel — with the AutoCollectLoot → StrongMods precedent finally weighed against what the game's own loader does.

research only — no project code changed test suite untouched design artifact for #29 interacts: #34, #35

Scope & method

What was surveyed, and how

All 18 code-mod projects' .cs sources (the census: AuthZ 14 files, StrongUtils 30, StrongMods 18, CustomChatCommands 7, BloodRain 7, BountifulQuests 7, and twelve smaller mods), driven by greps for the duplication axes the task named: config loading, chat/message helpers, command registration, player/entity lookup, logging prefixes, zone/geometry code, audit hooks. Every claim below cites the file and line it was read from. Three things were measured rather than read:

  • The assembly references of the compiled AutoCollectLoot.dll (reflection over AutoCollectLoot/bin/Debug/, script kept at .scratch/strongcore-inventory/refs.ps1).
  • The IL of the game's Mod.loadAssembly and an all-types scan for AssemblyResolve wiring, via Mono.Cecil over the declared V3.1.0-b14 dedicated-server Assembly-CSharp.dll (.scratch/strongcore-inventory/modload-inspect.cs and modload-dump.cs, run with dotnet run).
  • The log-prefix tally: 29 distinct literal [Tag] prefixes across the mods' Log.* calls (grep pipeline in the session transcript).

Read for framing: issues #29, #34, #35 (gh issue view), CONTEXT.md, StrongUtils/README.md, .ai/test-idea-tool-gap-seed.md, and Tests/Tests.csproj plus Tests/ModLogic/StrongZoneTests.cs for blast-radius facts. XML-only modlets were not read end-to-end; nothing below claims anything about them.

Headline

The shape of the duplication

The repo does not duplicate one library — it duplicates two idioms, five times each: sending chat from the server, and loading hot-reloadable settings.

Six whisper call sites exist across five assemblies, one of them a line-for-line copy (comment included). Settings loading exists as two structural clones (AuthZ, BountifulQuests), one 213-line engine (StrongUtils), one hand-rolled watcher (CustomChatCommands), and one XML-properties reader (AutoCollectLoot) — plus the same WorldEnvironment.OnXMLChanged Harmony patch pasted into five mods. Both idioms are Strongheart-opinionated (the <save>/StrongMods/ folder, the BBCode whisper voice), which is exactly the StrongCore charter in CONTEXT.md.

The precedent, measured

The AutoCollectLoot → StrongMods precedent proves less than it appears to: the compiled DLL carries no reference to StrongMods at all.

The ProjectReference with Private=false produces build ordering and a clean staging folder, and ModInfo.xml declares the dependency — but AutoCollectLoot's C# uses no StrongMods type (its dependency is the <foreach> in Config/items.xml:3), so the compiler dropped the assembly reference. No mod in this repo exercises a cross-mod assembly reference at runtime today. A StrongCore DLL would be the first, and the game's loader makes that a genuinely open question on Windows dedicated servers (details in the mechanics section).

Found in passing: a name collision

Two unrelated classes are both named ConfigManager: AutoCollectLoot/ConfigManager.cs (21 lines — actually a C3-idiom properties reader) and StrongUtils/ConfigManager.cs (213 lines — the save-folder file engine). Under the AGENTS.md naming rule ("names must survive leaving their context") the AutoCollectLoot one fails; it should be renamed when C3 lands, not as its own effort.

API sketches

What the first two modules would look like

Sketches only — sized for the shared-source shape (types internal, namespace StrongCore, C# 9, compiled into each consumer). Signatures use only game types the mods already touch. 

// StrongCore/Settings/SaveFolderSettings.cs   — replaces the AuthZ + BountifulQuests clones (C1, C5)
namespace StrongCore {
  internal static class SaveFolderSettings {
    // <save>/StrongMods/<fileName>, seeding from <mod>/Docs/<name>.default.xml on first run.
    // Never throws: any failure logs through warn and returns null (caller keeps defaults).
    internal static XDocument LoadOrSeed(Mod mod, string fileName, Action<string> warn);

    // Same, rooted at the cross-save level (GetSaveGameRootDir) — CustomChatCommands' semantics.
    internal static XDocument LoadOrSeedShared(Mod mod, string fileName, Action<string> warn);

    internal static string PathFor(string fileName);          // no I/O; for log messages
    internal static IDisposable Watch(string fileName,
      Action<XDocument> reload, Action<string> warn);         // opt-in hot reload (C5)
  }
}

// StrongCore/Chat/Chat.cs   — replaces five whisper implementations (C2)
namespace StrongCore {
  internal static class Chat {
    // ProcessPackage semantics: the net package decides remote-vs-local delivery,
    // so the same call works on a dedicated server and a P2P host.
    internal static void Whisper(int recipientEntityId, string message);
    internal static void Whisper(ClientInfo client, string message);
    internal static void Global(string message);              // BBCode Supported, EMessageSender.None
  }
}

The one behavior decision hiding in C2: today's three mechanisms differ at the edges (client.SendPackage fails silently for a local/host player; ChatMessageServer takes a recipient list; ProcessPackage delegates the choice to the package itself). The sketch standardizes on the ProcessPackage variant — the one ChatCommandHelper and DLCC already chose, with the comment explaining why. Consumers of the other two mechanisms change behavior microscopically at those edges; that should be named in the migration commit, not discovered.

The per-save vs cross-save split (C1) is surfaced as two method names rather than a parameter because it is a semantic difference an author should choose consciously — CustomChatCommands' cross-save root looks deliberate (commands shared across worlds), and a shared loader must not quietly normalize it.

Mechanics

Shared source vs a StrongCore DLL — what the game actually does

What the loader does (read from IL, V3.1.0-b14 server unit)

Mod.loadAssembly decompiles to a two-way split: on a dedicated server on Windows (RuntimePlatform 2, 7, or 44 — WindowsPlayer / WindowsEditor / WindowsServer) it loads mod DLLs with Assembly.Load(SdFile.ReadAllBytes(path)); everywhere else — including Linux dedicated servers, which is production per CONTEXT.md — it uses Assembly.LoadFrom(path). An all-types Cecil scan (nested types included) found no AssemblyResolve handler wired anywhere in Assembly-CSharp.

Consequence: a mod DLL that references StrongCore.dll by assembly name must be resolved by the runtime against an assembly that was loaded from a byte array on Windows dedicated servers. Under .NET Framework fusion rules byte-loaded assemblies live in no binding context and are not found by name-based binding without a resolve handler; the game runs Unity's Mono, whose binding is historically more permissive. Which behavior Mono actually exhibits here is unverified — nothing in this repo exercises it (see the precedent finding), and this session ran nothing in-game. The wider 7DtD modding community does ship cross-mod DLL dependencies, which suggests it works — but that is recollection, not evidence, and it is exactly the kind of claim this repo measures before relying on.

What the repo already has, on each side

Already built for a DLL route

  • ModInfo v2 <Dependencies> parsing, validation and unload-on-violation: StrongMods/ModDependencies.cs, DependencyValidator.cs, ModUnloader.cs.
  • ModLoadTier AfterDependencies in build/Deploy.targets — load-order-by-intent already exists.
  • The Private=false ProjectReference pattern (AutoCollectLoot.csproj) keeps staging clean.
  • CONTEXT.md's own relationship model: "StrongMods and StrongCore are distributed separately so mods can declare dependencies on them."

Already true for a source route

  • #29's stated preference: a folder of .cs files compiled into each consumer via linked sources, wired by an opt-in build/ import.
  • Every DLL stays standalone — one folder into Mods/ and done, which is the accessibility ethos the whole repo is built on.
  • The repo builds and deploys the fleet as one solution, so "a fix rebuilds N consumers" costs one command.
  • No runtime binding question exists at all.

Recommendation

Milestone 1 is the shared source folder. The DLL door stays open — but it must be opened by a measurement, not an assumption.

The source shape wins the first milestone on every axis that is decidable today: zero runtime risk, zero operational surface for Hades, immediate availability to #34 and #35, and full reversibility (converting a linked-source module into a real StrongCore mod later is additive; the reverse — recalling a shipped DLL dependency from a fleet — is not). The honest cost: consuming types are compiled per-assembly, so mods can never exchange StrongCore types across the mod boundary, and CONTEXT.md's "distributed separately, declare dependencies" vision for StrongCore goes unfulfilled for now.

That vision conflict is real and is the owner's call, not this report's: CONTEXT.md describes StrongCore as a separately-distributed dependency; #29 prefers no runtime dependency at all. The two converge if milestone 1 ships as source and a later milestone graduates StrongCore into a mod once (a) something genuinely needs cross-mod type identity, and (b) the Windows-dedicated-server binding question has been answered by the proposed spike below. Until both are true, a DLL adds risk and buys nothing the source folder doesn't already deliver.

Concrete shape for the source route

  • A StrongCore/ directory holding module folders (Settings/, Chat/, …) plus a tiny non-deployable StrongCore.csproj (IsDeployable=false) that compiles every module standalone — the folder stays honest, the IDE and Tests/ get a compile target, and the later graduate-to-mod path is "flip the project's deployability and add ModInfo".
  • Opt-in wiring per #29: consumers declare <StrongCoreModule Include="Settings;Chat" /> between their two imports; a build/-level target expands each into Compile links on StrongCore/<Module>/**/*.cs. Module granularity keeps dead code out of small mods.
  • Types are internal in namespace StrongCore — no public duplicate types across assemblies, no accidental API for outside modders (matching "not intended for use by outside modders"), and reflection-based tests reach internals regardless.

Sequencing

How #34 and #35 order against the StrongCore milestone

Both extractions currently lean on the exact code StrongCore would absorb, so ordering is not cosmetic — done in the wrong order, each extraction mints a fresh copy of the thing StrongCore exists to deduplicate.

1 · StrongCore slice 1 Settings (C1+C5) and Chat (C2) land as shared source; AuthZ and BountifulQuests migrate their clone loaders as the proving consumers.
→
2 · #35 StrongAudit → AuthZ The move needs a chat helper: StrongAudit.cs:49 calls StrongUtils.Chat.Global for the ban announcement. With C2 landed it consumes StrongCore; without it, AuthZ inlines yet another chat implementation. Small mover — one 52-line class plus Harmony wiring.
→
3 · #34 StrongZones extraction The big mover. StrongZones consumes ConfigManager (StrongZones.cs:95,422) for its hot-reloaded strong_zones.xml; standalone, that infrastructure must come from somewhere. With C1 landed it links StrongCore source; without it, the new mod copies ConfigManager — a fifth settings implementation on day one.

Two more interaction facts worth having on the table for #34/#35 design, found during the survey but not decided here. First: the StrongSworn concept (C4) spans exactly the two mods being reorganized — ChatCommandHelper's cvar gate and StrongZones' strongsworn_only tag — so its StrongCore helper is best cut as part of #34, not before. Second: #35 moves an enforcing feature (StrongAudit auto-bans via SdtdConsole.ExecuteSync, StrongAudit.cs:47–49) into a mod whose declared posture is detect-and-log-only ("enforcement is out of scope" — #35). The consolidation either inherits an enforcement exception or gates the ban behind AuthZ's mode machinery; that tension belongs in #35's design, and its resolution decides whether C7's audit-prefix convention matters there too.

Blast radius the extractions inherit from Tests/

Tests/ModLogic/StrongZoneTests.cs reaches zone logic reflectively and pins both the assembly and the namespace by string: ModLogicHost.For("StrongUtils", …) and host.ModType("StrongUtils.StrongZone") (lines 30–32). The #34 extraction silently breaks these strings; repointing them is part of that migration's cost, and the same applies to any StrongCore migration that moves a type Tests names.

Proposal

First milestone, concretely

  1. Scaffold: StrongCore/ with the non-deployable compile-check project, a README stating the charter (Strongheart-opinionated, internal, not for outside modders), and the build/ opt-in wiring. Needs a human-created mod:StrongCore label per AGENTS.md.
  2. Module 1 — Settings (C1+C5): SaveFolderSettings as sketched. Migrate AuthZ and BountifulQuests (the identical clone pair — smallest, purest win). Leave StrongUtils' ConfigManager consumers alone until #34 forces the question, answering #29's "migrate immediately vs new code only" with: migrate the clones, leave the engine.
  3. Module 2 — Chat (C2): as sketched; migrate the six whisper call sites, naming the edge-behavior unification in the commit.
  4. Then #35, then #34 per the sequencing above, each consuming StrongCore instead of minting copies — with slice 2 (C3 worldglobal idiom, C4 triggers/StrongSworn, C6 chunk keys, C7 log prefixes) cut opportunistically as those efforts touch the relevant files.

Every numbered step is issue-sized and fits the repo's ~100-line-change discipline except the scaffold, which is structural boilerplate.

Proposed tickets

  • StrongCore milestone 1: shared-source Settings and Chat modules — the scaffold plus modules 1–2 above (type:feature, scope:repo-wide).
  • Spike: verify cross-mod assembly binding under the Windows dedicated server's byte-array load — two throwaway mods, one referencing the other, on a local Windows dedicated server; the result is the gate on ever shipping StrongCore as a DLL (type:research, scope:repo-wide, area:testing).
  • StrongCore slice 2: worldglobal config idiom, chat-command triggers, StrongSworn helper — C3, C4, C6, C7, cut as #34/#35 touch the files (type:feature, scope:repo-wide).

Evidence

What is verified, and what is not

Verified off-game

  • Every duplication cite above was read from the named file and line in this session.
  • AutoCollectLoot.dll's reference list (measured): mscorlib, Assembly-CSharp, 0Harmony, LogLibrary, UnityEngine.CoreModule, System, System.Core — no StrongMods.
  • Mod.loadAssembly's IL (dumped, decoded in full in the session): the IsDedicatedServer + platform-switch split between Assembly.Load(bytes) and Assembly.LoadFrom(path). The platform constants 2/7/44 were resolved against the unit's own UnityEngine.CoreModule.dll (WindowsPlayer / WindowsEditor / WindowsServer; LinuxServer = 43 falls through to LoadFrom), not recalled from memory.
  • No add_AssemblyResolve call site in any type (nested included) of the V3.1.0-b14 server Assembly-CSharp.

Not verified

  • Mono's actual binding behavior against byte-array-loaded assemblies — the crux of the DLL option, and the subject of the proposed spike. Community precedent is recollection, not evidence.
  • Runtime equivalence of the three chat mechanisms at their edges — read from source, never executed.
  • Anything about the game client, other game versions, or the XML-only modlets (not surveyed).
  • DynamicLandClaimCount.HandleChatMessage was cited only as a registered handler (HarmonyPatches.cs:56); its body was not read.
  • The suite was not run (no code changed); the parallel-session baseline of 415 green was taken on faith from the task brief.

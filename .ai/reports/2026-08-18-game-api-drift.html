The Drift CI Already Catches, and the Sliver It Doesn't

Gap S2 in the seed inventory claims "direct method/field refs + ModEvents handlers TargetResolver can't see" are uncovered drift surface. This effort measured that claim against every compiled mod DLL: 1,319 game memberrefs are already guarded by CI compilation, all nine runtime string-lookup sites resolve in all four restored trees today, and the genuinely uncovered residue reduces to one partial-drift hole in AuthZ and one dormant data-driven dispatcher.

What was attempted

The task, from .ai/test-idea-tool-gap-seed.md (gap S2): quantify how much of the mods' game-API surface is already guarded by CI compilation, build a detector for the rest — members resolved by name at runtime — and say honestly whether promoting any of it into Tests/ is worth it.

  1. Census — enumerate every MemberRef/TypeRef each mod DLL carries into a game assembly, using pure BCL System.Reflection.Metadata (the Tests/Fixtures/IlReader.cs precedent: read metadata directly, load nothing).
  2. String-lookup scan — decode every method body's IL and record each call to a known lookup API (AccessTools.Method/Field/Property/TypeByName/Declared*, Type.GetMethod/GetField/ GetProperty/GetType, Traverse.*, Assembly.GetType) with the nearest preceding ldstr (the name) and unconsumed ldtoken (the subject type), then resolve each site against all four restored trees under packages/.
  3. Cross-check the S2 claim about ModEvents handlers against the actual usage in source.

Everything ran from the repo root; the tool is StrongDev/.ai/tools/apidrift.cs:

dotnet run StrongDev/.ai/tools/apidrift.cs -- --selftest   # 8/8 pass
dotnet run StrongDev/.ai/tools/apidrift.cs                 # full scan; exit 0, output captured

Finding 1 — compilation already guards the overwhelming bulk

Every mod compiles against the game's own assemblies (ADR-0002), and CI recompiles every mod against both units on every push (#21). So every statically-compiled reference into a game assembly — every MemberRef and TypeRef row in the DLL — is already drift-guarded: a removed or renamed member fails the build before any test runs. Finding 2 — nine runtime string-lookup sites exist, and all resolve today

The genuinely compilation-invisible surface is name-based runtime lookup. The IL scan across all 18 DLLs found exactly nine sites. The ModEvents half of S2 is unsupported

Every ModEvents usage in mod source is the game's typed API — ModEvents.X.RegisterHandler(method) with typed delegate structs (ref ModEvents.SChatMessageData, …), verified by grep -rn "ModEvents\." --include="*.cs" across the repo (hits in AuthZ, BountifulQuests, CustomChatCommands, BloodRain, DynamicLandClaimCount, ChatCommandHelper — all typed registrations). A removed event or changed payload struct fails compilation. There is no name-based ModEvents surface to guard.

Finding 3 — the honest residue is two items, one of them dormant

compile-guarded
754 memberrefs + 565 typerefs into game assemblies, plus every typed ModEvents registration and every nameof-derived lookup string. Re-verified against both units on every push (#21).
suite-guarded
Every [HarmonyPatch] attribute target and TargetMethods() provider — Tests/TargetResolver.cs resolves attributes and invokes providers against both units; an empty or throwing enumeration fails (CheckTargetMethodProvider, TargetResolver.cs:123-141).
soft-covered
AuthZ ProcessPackage, total loss: if a game update renamed ProcessPackage everywhere, InvariantEngine.PatchTargets() would skip every package and yield zero targets — which the suite fails on. Caught, but only at the all-or-nothing granularity.
uncovered
AuthZ ProcessPackage, partial loss: one guarded package type losing its declared ProcessPackage(World, GameManager) — rename or signature change — while others keep theirs. FindProcessPackage returns null for it, PatchTargets() logs a warning and skips it (InvariantEngine.cs:102-106), the enumeration stays non-empty, the suite stays green, and that packet type silently goes unenforced.
uncovered · dormant
StrongMods <function> dispatch: type/method names arrive from patch XML at load time (foreach.md §Custom functions). Statically unresolvable by design. Currently dormant: grep -rlE "function=|<function" --include="*.xml" */Config/ matches no shipped file.
Headline: after accounting for CI compilation and the existing suite, gap S2's real uncovered surface across all 18 code mods is one partial-drift hole in one mod (AuthZ's per-package ProcessPackage resolution) plus one dormant data-driven dispatcher (StrongMods <function>, unused by any shipped Config today). No currently-broken reference exists: the scan exits 0 with every site resolving in every tree. The seed's S2 row — "unblocks most StrongUtils commands, CustomChatCommands, StrongFill" — is unsupported: those mods contain zero string-based game lookups; their whole game surface is compile-guarded.

The tool: apidrift.cs

StrongDev/.ai/tools/apidrift.cs, a file-based C# app on the loclint.cs precedent. Pure BCL — System.Reflection.Metadata for metadata, operand sizes from System.Reflection.Emit.OpCodes (the IlReader.cs trick), no assembly loading, no game dependencies. It discovers every tree under packages/ (both units × both restored versions), censuses each mod DLL's memberrefs, IL-scans for lookup calls, and resolves each site per tree with lazy per-assembly member indexes that walk base chains (Declared* APIs checked declared-only, matching Harmony's semantics). Exit 1 on any resolution failure, so it can gate if ever wanted.

--selftest runs 8 embedded cases: colon-form "Type:Member" splitting, ldtoken/ldstr window pairing across GetTypeFromHandle, window-breaking on unrelated calls, dynamic-subject detection, argument-array stelem popping (both directions), BCL classification, and one end-to-end case that decodes the tool's own compiled IL and finds a planted Type.GetMethod site.

Two bugs the run itself caught (and their fixes)

  • Argument-array mis-attribution. The first scan reported AuthZ's site as DeclaredMethod(GameManager, "ProcessPackage") → MISSING ×4. False positive: the last ldtoken before the call was typeof(GameManager) from the new[]{typeof(World), typeof(GameManager)} argument array, not the subject (which is a loop variable). Fix: types live on a small stack and stelem pops them — a typeof stored into an array can never be the subject. Selftest cases 5b/5c pin both directions.
  • BCL-as-game census inflation. mscorlib/System.* physically live in the game's Managed dir, so "is it in the tree?" classified every string.Format as game API (first run: 1,848 "game" method refs, BCL column zero). Fix: BCL classifies first. Corrected totals are in Finding 1.

Known limitations (deliberate for a prototype)

  • Name-only resolution. A signature change that keeps the name passes — exactly the AuthZ signature risk noted above. Signature-aware checking needs blob decoding of the found member and the call site's argument array; not built.
  • Linear window heuristic, not dataflow. Names built at runtime surface as <dynamic-name>; a subject loaded from a local surfaces as <dynamic-subject> and downgrades to a "declared by N types in Assembly-CSharp" check.
  • nameof-blindness. IL shows a string either way; the source-form column in Finding 2 was established by reading the cited lines, not by the tool.

Decisions and trade-offs

  • IL scan over source grep as the primary detector. Source grep misses nothing today (it found the same sites first), but IL is the ground truth for what actually ships, catches lookup calls hidden behind helpers, and gave the census for free from the same reader. Trade-off: the nameof distinction is lost and had to be recovered by reading source.
  • Resolved against all four restored trees rather than only the two dev-version units — cheap once the lazy index existed, and it makes the "no broken reference exists today" claim exactly as wide as what CI tests (#37 made per-pin coverage meaningful).
  • Name-only member matching. Signature-aware matching would roughly double the tool for one known beneficiary (AuthZ). The partial-drift hole is better closed at the enumeration level (see the ticket) than by deepening this scanner.
  • Kept as a StrongDev ad-hoc tool, not promoted. See the recommendation.

Recommendation: do not promote the scanner into Tests/

A standing S2 test would re-verify, on every run: four nameof sites the compiler already guards, two mod-internal sites, two data-driven sites it cannot resolve anyway, and one dynamic-subject site it can only check as "the name exists somewhere". That is not worth a permanent fixture. The measured facts point at two narrow, cheaper actions instead:

  1. Close the real hole where it lives — partial enumeration drift in TargetMethods()/manifest providers. The suite already invokes them per tree; it only checks non-empty. Asserting enumeration parity (same target identities across the trees a mod declares, or against a declared expected set) converts AuthZ's silent per-package skip into a visible diff. Small, reusable across any future multi-target mod, and it also catches the signature-change case because FindProcessPackage matches on signature. Proposed as a ticket below.
  2. Keep apidrift.cs as an ad-hoc advisory to re-run at game-version adoption time (the moment drift actually happens), alongside the census as documentation of why S2-style gaps should be measured against CI compilation before being scheduled.

What remains

  • The parity guard itself — the ticket above; deliberately not built here because Tests/ is owned by a parallel agent this session.
  • Signature-awareness in apidrift, if it ever graduates — name-only is the biggest honesty gap in its verdicts (it would have called a ProcessPackage signature change "resolves").
  • The <function> dispatcher when it wakes up — the first shipped Config using it creates real statically-unresolvable surface. Unverified: whether Tests/Patcher/PatchApplicationTests.cs's replay would fail on an unresolvable function (the engine logs Log.Error, and the replay fails on undeclared warnings — plausible, but not tested in this effort).
  • Traverse and delegate-based lookups — the scanner knows the APIs but found zero uses; if a mod adopts Traverse chains, the subject-tracking heuristic will need work (it does not follow instance dataflow).
  • AuthZ's 19 "other" census refs — TypeSpec parents the minimal decoder does not name; believed to be generic instantiations, unverified.

Guard sketches for the top five

Guard 1 · ADR-0001 absence test · ~10 lines in ProjectConventionTests

A fourth rule alongside B/C/D — the one placement fault the import-order rules cannot see, because every csproj still reads perfectly:

[Fact]
public void F_No_auto_imported_MSBuild_files_exist() {
  // ADR-0001: auto-import fixes the position and this repo needs both positions. An added
  // Directory.Build.props reaches every SDK project invisibly; the canonical fault is the OutDir
  // latch, where OutputPath reads back correct while the assembly lands somewhere else.
  var offenders = Directory.EnumerateFiles(repoRoot, "Directory.Build.*", SearchOption.AllDirectories)
    .Concat(Directory.EnumerateFiles(repoRoot, "Directory.Packages.props", SearchOption.AllDirectories))
    .Where(IsSourceProject)  // the existing filter: skips bin/obj/.scratch/vendor/.git/.ai
    .ToList();
  Assert.True(offenders.Count == 0, /* teach ADR-0001 in the message */);
}

One decision: packages/ must also be excluded — restored NuGet packages can legitimately contain such files, and IsSourceProject today does not filter packages (it never needed to for csproj scans). One added token in that filter, scoped to this rule or shared, implementer's choice.

Guard 2 · target-sync test · normalize-and-diff, no build

Read both files as text, extract each duplicated target (_ValidateGameTreeDeclaration, _VerifyInstallVersion), strip XML comments, collapse whitespace, and assert equality modulo an explicit allowlist of adapted lines — today exactly one, the _DeployInstallRoot assignment. The allowlist is asserted too: an unexpected new difference fails with a message quoting both sides, and a difference that disappears (someone unified the files properly) fails the allowlist check, prompting the test's own retirement. Fragile to reformatting by design — reformatting a safety target is exactly when a human should re-diff the pair. Measured baseline for the allowlist:

< <_DeployInstallRoot>$([MSBuild]::NormalizeDirectory('$(MSBuildStartupDirectory)', '$(ModsDir)', '..'))</_DeployInstallRoot>
---
> <_DeployInstallRoot>$([MSBuild]::NormalizeDirectory('$(MSBuildStartupDirectory)', '$(DeployRoot)', '..', '..'))</_DeployInstallRoot>

Alternative considered: deduplicate the targets into a shared file both import. Rejected here — Overlay.targets is self-contained by design ("never combine with the other entry points", its header), and a shared import would re-couple what #25 deliberately separated. The diff test buys the sync without the coupling.

Guard 3 · load-order sort facts · two layers, split by cost

Layer (a), cheap, now: a unit test asserting the documented chain under the culture-aware comparison the header claims — string.Compare(x, y, StringComparison.InvariantCulture) over ["_disabled", "0_TFP_Harmony", "000000-StrongMods", "MyPlainMod", "Z_Foo", "Z-IM-PZ-Compat", "ZZ_Bar", "ZZZZZZZZZZ_Baz"], plus the negative fact (ordinal sorts ZZ_ before Z_). This pins the header's arithmetic and catches any prefix edit that breaks the banding — but it re-encodes the assumption about which comparer the game uses.

Layer (b), the real guard: resolve the game's own mod-folder sort and run it. The suite already loads game assemblies for both units (TargetResolver, the transpiler runner), and #57 itself suggests exactly this. Unverified as of this sweep: which method in the game performs the sort (likely in ModManager; the repo's own memory notes say to read ModManager/GameIO rather than assume). The ticket should start with that one-time IL investigation; if the sort site is reachable, invoke it against a fixture folder list per unit and assert the chain; if not, assert the comparer kind from its IL as a drift tripwire.

Guard 4 · XmlLint fires · one negative-path Workspace test

The BuildPathResolutionTests.Workspace pattern already builds synthetic modlets in a temp tree. Add one test: write a modlet whose Config/broken.xml is malformed, build (not deploy), assert exit ≠ 0 and the log carries broken.xml( — the file(line,col) shape the task emits (build/XmlLint.cs:32). A second build with -p:XmlLintEnabled=false must pass, pinning the escape hatch. Because the synthetic project imports the real build/Modlet.targets, the test covers the wiring (import present, hook name valid, condition spelled right) — the parts a unit test of XmlLint.cs alone could not see. Cost: one shelled build, ~2s, alongside the four tests in that class that already shell -t:Deploy builds.

Guard 5 · tier map + StrongMods First · four evaluation pins and a scan

Evaluation-only, using the existing Workspace: for each tier, dotnet msbuild <probe> -getProperty:ModDeployName -p:ModLoadTier=First must yield 000000-PathProbe (and ZZ_, ZZZZZZZZZZ_ for the others; Last and LocalConfig deliberately collide — assert that too, it is documented intent at build/Deploy.targets:49-51). Plus one XDocument line in ProjectConventionTests: StrongMods declares ModLoadTier=First — the executable form of AGENTS.md's "StrongMods loads first", which the breadth-first patcher's whole visibility contract hangs on.

Deliberately down-ranked, with reasons

  • The no-op VSTest / _IsProjectRestoreSupported targets (#57 seed; build/Modlet.targets:51-63, Overlay.targets:55-68). The #51 failure mode is loud: a bare entry point missing VSTest fails dotnet test StrongMods.sln with MSB4057, and CI runs that on every push — the suite run is already the executable guard. The genuinely silent residue is only NU1503 warnings returning if the restore probe broke. Damage-if-silently-broken ≈ nil; no guard proposed.
  • FrameworkPathOverride / compile-against-the-game (ADR-0002) — every build of every mod is the test, and the failure is a wall of compile errors funneled into VerifyGameInstall's one readable message. Not silent.
  • Evaluation-survives-errors ("all errors fire at target time", build/GamePaths.props:66-67) — a regression fails the very next -getProperty run and every IDE load. Loud.
  • BloodRain's CopyDocumentationFilesFromPackages (Cronos.xml deploys beside Cronos.dll) — real prose-only behavior, but single-mod, low blast radius. Fold into any future deploy-shape assertions rather than guarding alone.

Detailed review

P0 — selector interception

Evidence. The implementation puts the Harmony prefix on XmlFile.GetXpathResultsInList, the plan’s verified funnel. Its fast path leaves expressions without sm: to vanilla. The prefix is category-gated by Config.XPathInheritanceEnabled and ModApi.InitXPathInheritance. PatcherHost applies that category and the fourth conformance test drives a marked selector through real singlePatch dispatch. Recommendation. Require it on both declared units in CI. Impact. The local proof covers the funnel; CI remains the game-version and Linux compatibility proof.

P1 — cache and mutation lifecycle

Evidence. The engine creates an evaluation scope around each marked XPath and indexes candidate keys only inside that scope. It keys the default population by the actual sibling parent and element name, and an explicit population by its XPath text. Recommendation. Preserve that boundary and retain the test where one command changes a parent then a later command resolves a child. Impact. A process-wide cache would make selector results stale after ordinary patch mutation; rebuilding per selector avoids invalidation logic.

P1 — chain damage is local

Evidence. The walk truncates only its current chain for multiple links, missing keys, duplicate keys, cycles, and the 64-hop backstop. It logs through the game logger. Recommendation. Build the planned row-by-row warning tests and tune messages to include the node and scheme arguments. Impact. This determines whether a malformed mod is diagnosable while unrelated selector matches continue to work.

P1 — #144 is an acceptance boundary, not a scope expansion

Evidence. The new #144 bug report records a shipped-patch regression test for a direct entity loot container, its immediate child, a transitive grandchild, and an incomplete child. The consumer selector intentionally uses direct @extends membership instead of sm:inherited, because the issue asks for one level only. Recommendation. Preserve that narrow selector. Impact. #144 proves the StrongMods patch pipeline still composes with a real dependent mod while avoiding an accidental product commitment that every descendant should generate loot.

P2 — author documentation

Evidence. StrongMods/Docs/inheritance.md now describes the function signatures, return-order caveat, shorthand, population default, data failures, and interaction with foreach variables. Recommendation. Treat each behavior as a conformance-test row, as the plan requires. Impact. The feature is a developer tool: an API example without the caveats would invite subtly wrong selectors.

Naming — sm:inherited

The name was ratified because it reads naturally in predicates, although its operation begins with the current node. The new docs use “declared or inherited” at every semantic explanation. Recommendation: keep this pairing; changing to effective would be technically plainer but less immediately readable in the common query.

Naming — sm:chain

“Chain” accurately describes the node plus successive ancestors without promising an ordering XPath may later change. It includes self by design. Recommendation: keep it and do not introduce ancestors or a boolean self flag before a real strict-descent caller establishes the need.

Naming — #Name

The leading marker reads as a compact property reference and cannot be confused with general XPath. It is limited to select and link, where it expands to the game’s flat property shape. Recommendation: retain the limitation; extending it to keys would make an already-clear @name less explicit.

Naming — XPathInheritance

The category, feature class, configuration switch, and report all use the same concept phrase. That makes the feature discoverable in patch configuration, source search, and an eventual user issue. Recommendation: keep this vocabulary rather than splitting it across “extension functions,” “resolver,” and “selector patch.”

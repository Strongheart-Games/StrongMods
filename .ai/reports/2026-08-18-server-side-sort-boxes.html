Server-Side Sort Boxes

Three shipping 7 Days to Die sort tools, read end to end against the game's own decompiled source, and measured against what StrongBoxes is trying to become. The headline results: the argument against custom blocks is wrong but the preference for sign names is still right; container contents are client-authoritative, which decides both the locking discipline and the fate of the mailbox idea; party membership does not affect permissions but allies do, and that is a problem; and the production mod on Hades reaches outside the land claim it promises to respect.

Ten things that matter

  1. Container contents are client-authoritative. The client mutates its local copy and pushes the whole item array; NetPackageTileEntity.ProcessPackage applies it with no sender validation and no merge. Everything else in this report follows from that one fact.
  2. "Custom blocks force a client download" is false. The server ships its patched blocks.xml and localization to every client. Both block-based mods here are server-side-only and EAC-friendly. Your preference for names is still right — for different reasons.
  3. Only 6 of 1,563 storage blocks can carry a sign at all, and only 3 of those also have a lock. That is the hard price of a name-driven design, and it is the single biggest constraint on StrongBoxes.
  4. Party membership does not affect permissions. Allies do — and that is an escalation. Vanilla does not let an ally open your locked box, but ServerTools' sorter will write into it.
  5. RoboticInbox reaches outside the land claim it promises to respect. Measured: an inbox two blocks from its claim edge probes 10,146 positions outside the claim, up to 18 blocks past it. This mod runs on Hades.
  6. ServerTools' only in-use guard is dead code. It passes the composite where the lock was registered on the feature, and LockEntry.Equals is reference equality, so it never matches.
  7. RoboticSorter's trigger probably does not fire the way it intends on a dedicated server. It hooks TileEntity.SetModified, which the client-push path never calls.
  8. Top-up-only is not the conservative choice — it is a silent exclusion. Every quality item has a stack limit of 1, so no tool, weapon or armour piece can ever be topped up. #31's open question has a clear answer.
  9. There is no concurrency to get wrong. Everything is main-thread. Deadlock is structurally impossible. The real hazards are interleaving across frames and last-writer-wins replication.
  10. mailbox as "anyone deposits, only the owner withdraws" is not implementable as prevention in 3.1.0-b14. It has to become an open-time permission instead.

Detecting the sort box

Two independent axes get conflated in every discussion of this: what marks the box (block identity versus player-written name) and when you find out (which hook you patch). They trade off differently and should be decided separately.

The client-download argument does not hold

Correction to a premise

The common objection to custom blocks — that a new block forces every player to download the mod — is false in 3.x. WorldStaticData.SendXmlsToClient ships the server's fully-patched blocks.xml to every connecting client, localization streams alongside it, and assignIdsFromMapping reconciles block ids by name. A block built only from vanilla classes and vanilla art works on a stock client.

Both block-based mods here prove it in production. Each defines its blocks by <property name="Extends" value="cntSteelWritableCrate" /> and only retints them — no new mesh, no new texture. RoboticInbox's README states plainly: "Works on Dedicated Servers (EAC can stay enabled)."

So the case for sign names has to be re-based. The durable advantages are real and they are the ones you named: a name retrofits onto a box the player already owns, it is revoked by retyping, it is self-documenting in a shared base, and — the one that matters most architecturally — a vocabulary scales as N strings rather than N×M block definitions. That last point is decisive for what you want to build: a box may need to be both sort and nosort-adjacent, or both a mailbox and a labelled ammo box, and it can only ever be one block. RoboticInbox needs 24 block definitions plus five supporting XML files to express one behaviour in eleven colours.

The price, and it is steep

A census of the 3.1.0-b14 blocks.xml with Extends resolved: exactly 6 of 1,563 storage-bearing block definitions carry a TEFeatureSignable — the wood, iron and steel writable crates, secure and insecure. Only 3 of those also carry a TEFeatureLockable (the non-Insecure variants).

Two consequences. Your keyword vocabulary can only ever be written on writable crates, where RoboticInbox's block tag reaches all 1,563. And a mailbox keyword on an Insecure crate has no ACL to lean on and must fall back to TileEntityComposite.Owner. If 6 blocks proves too narrow, the cheap fix is to patch TEFeatureSignable onto more existing containers via XML — it needs all four of FontSize/LineCount/LineWidth/LineSpacing or TEFeatureSignable.Init logs an error — rather than defining new blocks.

The hook axis, which is where the real difference is

TEFeatureStorage.OnUnlockedServer has one caller, LockManager.UnlockRequestServer. It fires exactly once per lock release and it carries _unlockingPlayerId. Despite the name it is a close event: the "lock" is the exclusive-access lock a client takes when it opens a container, not a padlock. StrongBoxes' README is right about this.

The ordering is better than it looks. On close, XUiC_LootWindowGroup calls te.SetModified() first, then SetUserAccessing(false), then UnlockRequestLocal(). The player's final contents are therefore already on the wire before the unlock, which is exactly why sorting on unlock is the right choice.

RoboticSorter's hook does not do what it looks like it does

It patches TileEntity.SetModified. But the server's client-push handler, NetPackageTileEntity.ProcessPackage, reimplements the server half inline — it calls read, NotifyListeners, SetChunkModified and SendPackage, and never calls SetModified(). I verified this directly against the decompiled package.

What does call it server-side is PopulateTE, reached from OnLockedServer — that is, when a player opens a container. So on a dedicated server RoboticSorter appears to trigger on open, against the pre-edit contents, rather than on the content change it is written to respond to. If you were considering the SetModified hook, this is the reason not to.

StrongBoxes should switch from Prefix to Postfix, and wrap the body

UnlockRequestServer removes each LockEntry before calling OnUnlockedServer, but clears singleLocks and keepOpenTimes only after the loop. A prefix that throws therefore leaves the player in playersWithLocks, and their next attempt to open anything is refused with "Invalid lock state for player N". It also suppresses vanilla's CheckDestroyTileEntity. RoboticInbox uses a Postfix wrapped in try/catch and has neither failure mode; StrongBoxes uses an unwrapped Prefix (StrongBoxes/StrongBoxes.cs:41-46).

Name matching is where a name-driven design actually breaks

ServerTools and StrongBoxes both match the whole sign for exact equality. I checked what a player can actually type: a storage box opens the signMultiline editor, a single 50-character field with on_return="NewLine". So "sort ", "sort\nkitchen" and "[FF0000]sort[-]" are all reachable input that silently disables the box, with no message and no visible difference on the sign face. The writable crate declares LineCount=3 — a keyword line plus a label line is the block's designed use, and whole-string matching forbids exactly that.

The prototype's BoxKeywordVocabularyTests runs all of these as executable cases. Whole-sign matching sees a bare keyword and misses every one of the five variants above; line matching with markup stripping catches all of them and still ignores "sort this out later", "assorted junk" and "needs sorting".

Distributed state, locking and interleaving

Settle the framing first: there is no concurrency here

Network packet processing, LockManager.Update, and every ThreadManager coroutine all run on the Unity main thread. Mutexes, volatiles and lock-ordering protocols would be pure ceremony, and deadlock is structurally impossible — LockManager has no blocking acquire, and mods hold nothing. Do not build a lock-ordering protocol for this. The one place a real data race can be manufactured is holding a stale TileEntity whose pooled Chunk the background chunk-save thread is serializing.

What is real is single-threaded interleaving across frames, plus a last-writer-wins replication channel with no merge.

The write path, and why it decides everything

client
Player drags an item. XUiC_LootContainer calls UpdateSlot then SetModified() on its local copy.
↓ NetPackageTileEntity, StreamModeWrite.ToServer — the whole array, not a delta
server — no authorization
ProcessPackage calls tileEntity.read(..., FromClient). No sender check, no distance check, no per-slot validation, no merge. The server's array is replaced.
↓ rebroadcast to clients within 192 m
other clients
Receive the new array — unless they have the box open, in which case TEFeatureStorage.read discards the item payload while IsUserAccessing() is true.

That last guard is client-side only. SetUserAccessing has exactly one writer in the whole assembly — XUiC_LootWindowGroup, the client loot window — so on a dedicated server bUserAccessing is always false and the guard never protects the server's copy.

Sorting into a box a player has open destroys items, silently

The sequence is: the sort removes items from the source and writes them into the target; the player who has the target open closes it; their client pushes the array it snapshotted when it opened, which does not contain the new items; the server accepts it. The items are gone from both ends. Nothing logs an error — the sort recorded success.

Tests/SortBoxes/ContainerInterleavingTests.cs runs this as seven executable cases, including the one that matters most for implementation: a check taken before a yield is already stale by the write. The window is not "at close" either — any client-side modification pushes the whole array, so it is "at any time while open".

The in-use guard, and the trap in it

ServerTools' guard never fires

LockEntry.Equals is reference equality on Target, and TEFeatureStorage.OnBlockActivated registers this — the feature. ServerTools passes the TileEntityComposite (Sorter.cs:60), which compiles cleanly and silently never matches. Its only concurrency protection is dead code.

RoboticInbox passes the ITileEntityLootable from its cast helper and works (StorageManager.cs:357-372). RoboticSorter has no check at all. If StrongBoxes takes one mechanical lesson from this report, it is: pass the feature, never the composite.

A related nuance worth writing down rather than cargo-culting: a source-side in-use check at OnUnlockedServer time is unreachable. UnlockRequestServer removes the lock entry before invoking the callback, and single locks are exclusive, so no player can be holding the source at that instant. RoboticInbox's source branch is dead in the normal flow. The check only becomes meaningful if work is ever deferred past that frame.

RoboticInbox's best idea, and its sharp edge

RoboticInbox patches TEFeatureAbs.CanLockOnServer to refuse the lock while an inbox is distributing, so a player simply cannot open it mid-sort. That is genuine mutual exclusion on the source, it is the best single idea in the three mods, and it is the same seam that makes mailbox implementable at all (below).

The sharp edge: the ActiveCoroutines entry is removed by the coroutine's last statement, while two of its checks sit outside the try. Any escaping exception leaves the key in the dictionary forever, and the CanLockOnServer prefix then makes that inbox permanently unopenable for the rest of the session. If StrongBoxes ever defers work, model the run as an explicit token cleared in a finally, keyed by entity identity rather than position — position keys collide when a box is destroyed and rebuilt at the same coordinates.

Algorithms and what they cost

Container discovery is the whole cost story, and two of the four tools get it wrong by roughly three orders of magnitude. The question you ask the world decides everything: "is there a container at this coordinate?" costs one probe per coordinate, while "what tile entities does this chunk have?" costs one visit per entity that actually exists. Both bottom out in the same Chunk.tileEntities dictionary — but containers are sparse by construction.

RoboticSorter cube, r=30 226,980
RoboticInbox shell, range 20 74,620
Chunk walk (9 chunks × 40) 360

World.GetTileEntity calls per run, measured by Tests/SortBoxes/SortScanStrategyTests.cs. The chunk walk covers a block volume of 589,824 while visiting 360 entries — 630× cheaper than the radius-30 cube. RoboticSorter's figure is also per trigger, and its trigger is a hot path: 100 fires is 22,698,000 lookups.

StrongBoxes already has the right discovery geometry

Its 3×3 chunk window over Chunk.GetTileEntities().list is the correct shape, and it is provably minimal for its radius. Chunks are 16 wide in X and Z (toChunkXZ is v >> 4) and 256 tall (toChunkY is v >> 8), so a 3×3 window's guaranteed horizontal reach is exactly 16 blocks, against a MaxDistance of 15.

That one-block margin is a coincidence. MaxDistance lives in SortBoxes.cs:7 and the ±1 chunk loops live in StrongBoxes.cs:18-19, in a different class in a different file, and CalculateAdjacentChunkKeys takes no radius parameter. At 17 a box flush against a chunk edge silently stops seeing containers on the far side while still seeing them on the near side — direction-dependent, position-dependent, invisible in logs. The prototype's ChunkWindowGuaranteedReach computes the 16 and a theory asserts the invariant.

The matching inner loop is where the remaining work is

All three references walk targets-major and re-scan every target's slots for every source item, costing |targets| × |source slots| × |target slots|. Indexing the targets once by item type turns the product into a sum. Measured on a base of 60 specialised containers of 45 slots with a 45-slot sort box:

Both plans place identical items (4,500 units at 45 slots) — the index is behaviour-preserving. Growth with base size is the same story: at 240 containers, 486,000 comparisons against 10,845. Building the index after a global distance sort also makes every candidate list arrive nearest-first for free, which is the fix for the ordering defect below.

Two cheap wins the references mostly miss. Break out the moment the source empties — ServerTools is the only one that checks at all, and its check sits one level too coarse (top of the chunk loop), while RoboticInbox walks every remaining shell of its 74,620-probe box after the inbox is already empty. And call SetModified() once per touched container, not per item: it serializes the entire tile entity — every feature, every slot, the sign text — and broadcasts it to clients within 192 m, and AddItem calls it internally on every successful placement.

Matching and tie-breaking

All three tools answer "which box may receive this?" with the same coarse predicate, and none of them answers "which box wins?" at all — because none ever scores candidates against each other. Each greedily drains the source into whatever its scan reaches first.

The grain of the match

ToolComparisonPlayer-visible effect
RoboticInboxitemValue.ItemClass reference equality All pickaxes pool regardless of quality. Two unresolvable types both return null and compare equal — a false match.
RoboticSorteritemValue.type Same grain. Omits CanStackWith's texture test, so differently painted block stacks merge and the player's blocks get silently repainted.
ServerToolsHasItem(itemValue) Same grain, via the game's own helper.

ItemClass equality and .type equality are identical for every non-quest item, because ItemValue.ItemClass returns the shared ItemClass.list[type] instance. Prefer .type — it is what the game's own HasItem and TryStackItem use, and it avoids both of ItemClass's failure modes. For the merge decision use ItemStack.CanStackWith rather than raw .type, which adds the texture test.

#31's open question answered: top up and place new stacks

ItemClass.LateInit() forces Stacknumber.Value = 1 for every item where HasQuality is true. So MaxCount is 1, CanStackPartly returns false, and TryStackItem can never move any tool, weapon or armour piece.

A top-up-only sorter is therefore not the conservative reading — it silently excludes the entire item category players most want sorted. All three references place new stacks. The prototype demonstrates it: Top_up_only_can_never_move_a_quality_item_because_its_stack_limit_is_one.

Tie-breaking: the scatter problem

When two boxes both already hold nails, every reference tool picks whichever its scan reached first — RoboticInbox by shell order (correct in principle, broken by the typo below), RoboticSorter by raw x/y/z loop order, ServerTools by Dictionary enumeration order inside each chunk. The prototype shows the consequence directly: feed the same two candidates in the opposite order and the nails land in the other box. That is a property of the scan, not of anything the player chose, so rebuilding the same base rotated changes where things go.

The recommended ranking is a documented total order, so it is testable and has no ties:

  1. Sign-declared priority, if present.
  2. Count of that item already held, descending.
  3. Euclidean distance, ascending.
  4. World position, lexicographic — the final discriminator.

Existing-quantity earns its place above distance because it is the only heuristic in the space that is self-correcting: a stray round in the wrong chest loses to the canonical stack, so misroutes heal instead of compounding. Most-free-space actively diverges and should be rejected. The prototype shows nearest and most-existing genuinely disagreeing, which is why this is a design decision rather than a detail.

Honour SlotLocks on the destination, not just the source

Neither AddItem nor TryStackItem consults SlotLocks — vanilla only ever uses locks as a source-side filter, so the destination case is latent until a mod writes from the server side. RoboticInbox writes into locked slots and then calls StackSortUtil.CombineAndSortStacks with default arguments, where the game's own sort button passes the player's lock mask — destroying exactly the layout the lock exists to preserve. RoboticSorter ignores SlotLocks entirely.

Your flagged question: what an "ally" is, and whether party matters

Party membership does not affect anything. World.GetLandClaimOwner — the method ServerTools calls — never touches EntityPlayer.Party. A party-aware variant exists, World.GetLandClaimOwnerInParty, and there party is an additional restriction, not a grant: it requires both IsAlly and player.Party.ContainsMember(...). Its only two callers in the entire assembly are Discord rich presence and a Twitch UI flag. Neither is a permission decision.

An ally is AllyStore.GetStatus(a, b) == AllyStatus.Allies — a mutual, explicit, persistent invite/accept relationship (NotAllied → OutgoingInvite / IncomingInvite → Allies) stored in players.xml. It is not the party, not Steam friends, and not the container ACL.

And here is the escalation. Vanilla does not let allies open your locked containers: TEFeatureLockable.IsUserAllowed is IsOwner(id) || allowedUserIds.Contains(id), and allies are never consulted. So ServerTools' Ally grant lets the sorter write into a box the acting player is forbidden to open by hand. Never accept Ally alone as a grant.

The two models, contrasted

(a) Lock/password matching — the password is the capability

The elegance is real: no identity infrastructure, no configuration, no group data structure. A player who knows a password can already open that box by hand, so moving items between two boxes sharing a hash grants no authority they lacked. A clan sets one password and the whole base interoperates.

The failures are equally real. An unlocked box is fair game to anyone's inbox — and most players do not lock storage inside their own base, because it is tedious. A shared-password base leaks between players: the hash is a 32-bit GetStableHashCode().ToString("X8"), so two unrelated players who both pick 1234 get interoperating containers with no owner cross-check. And nothing stops you placing an inbox near a stranger's chests and letting your overflow flow into their base.

The sharpest irony, and the primitive nobody uses

The game already maintains the list this model wants. TEFeatureLockable.allowedUserIds is populated precisely when a non-owner types the correct password. That is "everyone who has proved they know the secret" — the password model's semantics with an identity attached — and none of the three mods ever reads it. One caveat to record: the ACL is wiped whenever the owner changes the password, so it is not a stable allow-list.

(b) Land-claim ownership — territory as authorization

The elegance is that it maps to the game's own model, it makes lock state correctly irrelevant, and above all it knows who opened the box. That is structural, not incidental: RoboticInbox's postfix takes only __instance, and RoboticSorter's trigger has no actor in scope even in principle. Password matching is what you build when you have no actor.

The failures: outside a claim the answer is None, which is blocked — so unclaimed bases get nothing, silently, with not even a chat message. The useful inverse is that ServerTools cannot dump into a stranger's unclaimed box, which is the safer failure direction. Two further hazards if you adopt it: claim ownership is 2D with no vertical bound, and on any non-survival game mode GetLandClaimOwner returns Self for every position on the map, turning the gate into a no-op.

The invariant to design to

A sort may only do what the acting player could have done by hand.

All three tools violate it, in different directions. RoboticInbox and RoboticSorter reach into a stranger's unlocked box the player never opened. ServerTools reaches into an ally's password-locked box the player cannot open. Stated as an invariant it also resolves future vocabulary questions automatically — mailbox is precisely a deliberate, explicit exception to it, which is exactly the kind of thing that should require a keyword rather than fall out of a permissive default.

The sign-name-as-command framework

ServerTools is the only prior art that treats a sign as a command vocabulary. It is not a framework — it is five independent copies of the same three lines, and every defect in it traces to that absence.

What ServerTools actually has

Five keywords on five unrelated classes: sort/auto sort/dump (Sorter), vault, bank, wall, plus auction. No interface, no dictionary, nothing that can enumerate the vocabulary. Precedence is emergent from statement order in one Harmony postfix — Vault's handler runs before Sorter's, so two features on the same word resolve by which if was typed first, and Vault wins silently because it empties the container first. The three sorter names are pure aliases; nothing distinguishes dump from sort.

The exclusion list teaches the real lesson

ServerTools' entire "nosort" mechanism is one line: 

if (text == Vault.Box_Name || text == Box_Name1 || text == Box_Name2 || text == Box_Name3)
    continue;

It reaches into Vault.Box_Name and is blind to Bank, Wall and Auction — all three of which are physical storage containers identified by sign text. I verified this directly: a box named bank or wall is a valid sort target and will receive items. Auction reads items[0] positionally, so a stray dump corrupts a listing. The line also reserves vault even on servers that never enable Vault.

This is the coupling that breaks as keywords multiply: every feature must know every other feature's keyword, so adding the Nth keyword needs N−1 edits in files you are not touching, and forgetting one is silent. Worse, because exclusion is expressed by naming the box something else, there is no way to make a container ineligible without also changing what it is — naming it vault makes it a vault. Your proposed nosort is exactly the missing primitive: an exclusion marker that is not also a behaviour marker.

Normalization drift is the other symptom. Config lowercases Sorter's and Vault's names at load but stores Bank's and Wall's raw, and comparisons apply .ToLower() inconsistently. The live defect: with Box_Name="Bank" configured and bank on the sign, /deposit finds the box and /withdraw does not. Same box, same keyword, opposite answers. Vault reads its own keyword two different ways in the same file.

Grammar: use a sigil

The hard constraint the prior art never states is that the sign holds 50 characters total and is the same surface players use for real labels. Weighed against that:

FormVerdict
sort (bare) Best discoverability, but collides with innocent labels and cannot coexist with one. Fatal.
sort:ammo Expressive, but presupposes parameters nothing needs yet, and : is plausible in a real label (Ammo: 9mm).
Multi-line directive block 50 characters across all lines makes it absurd, and it steals the whole sign.
#sort Recommended. One character, never typed accidentally, reads as machine-directed, greppable in logs and support threads.

The sigil solves ServerTools interop for free

Both mods hook OnUnlockedServer and both would fire on a box named sort, sorting it twice under different semantics and different access models. But #sort fails ServerTools' whole-string text != Box_Name1 comparison, so the two vocabularies become disjoint by construction with no interop work at all. This is the strongest practical argument for the sigil. Document the migration as "add a #, keep your label."

Scan every line for #-prefixed tokens and leave all other text alone as the player's label. A box reading Ammo / #sort #nosort is a labelled ammo box that sorts and refuses to be a target. Normalize at exactly one boundary — trim, split on newline and whitespace, ToLowerInvariant(), keep # tokens — and never compare raw text anywhere else. Use ToLowerInvariant, not ToLower: StrongBoxes currently uses the culture-sensitive form, and on a tr-TR server I lowercases to U+0131, which is ordinally different from i. Harmless for sort; fatal for a future #inbox.

The architectural split that decides the registry's shape

A keyword is either a trigger or a property, and the current bus can only hold triggers

#sort is a trigger: it has a firing event (this box closed), it acts, it is done. #nosort and #mailbox are predicates on a container — nothing happens when a #nosort box closes; the keyword exists to be asked about by a different feature, at a time that feature chooses.

StrongBoxes' ConcurrentBag<Listener> fires only on the box the player closed, so nosort has literally nowhere to hook. Model the vocabulary as a queryable property store first, with trigger dispatch layered on top — not as an event bus.

The current bag has four more problems worth naming: every listener re-parses the text and invents its own matching rule (the exact divergence that produced ServerTools' Bank asymmetry); ConcurrentBag enumeration order is explicitly unspecified, so two matching keywords fire nondeterministically — ServerTools at least had deterministic ordering; nothing detects two listeners claiming one word; and the vocabulary cannot be enumerated, so there is no help text, no console command and no misspelling detection. 

public interface IBoxKeyword {
  string Token { get; }          // "#sort" — the vocabulary, enumerable
  string HelpText { get; }       // for a console command and chat errors
  KeywordKind Kind { get; }      // Trigger | Property
}
public interface ITriggerKeyword : IBoxKeyword {
  int Priority { get; }                                  // deterministic order
  void OnClose(TileEntityComposite box, int playerId);   // player id retained
}

static void Register(IBoxKeyword k);                     // throws on duplicate Token
static IReadOnlyCollection<IBoxKeyword> Vocabulary { get; }

Register throwing on a duplicate turns ServerTools' silent statement-order collision into a startup error. The prototype implements this shape and tests the refusal.

On caching the sign reads: do not, initially. A close costs on the order of 10²–10³ candidates, each one array index plus a string read plus a tokenize. RoboticInbox already tolerates 74,620 GetTileEntity calls per close. A position-keyed cache is also a correctness hazard, because the signable and the storage are separate lock targets on the same composite — a second player can rewrite the sign while a first has the box open. Re-evaluate keywords at the moment of action regardless.

Mailbox: a real feasibility verdict, and it is negative

Directional access control on a container is not implementable in 3.1.0-b14

There is no server-side hook on taking an item out. There is no request/response for storage item moves at all. TEFeatureStorage has no mutation callback, and NotifyListeners is a client-UI mechanism with no server listeners. The only seam is patching the packet handler and diffing against a snapshot — a revert, not a prevention.

And the revert does not work, for two independent reasons.

The offending client ignores it. TEFeatureStorage.read discards the inbound item payload entirely while that client has the box open, so a mid-session restore broadcast is read and thrown away by the very client you are trying to stop. Their UI still shows the item gone, and on close they push their stale array back and re-remove it.

Reverting duplicates the item. The player's backpack is equally client-authoritative — NetPackagePlayerInventory and NetPackageBag are both ToServer and carry a whole cloned bag. There is no server-to-client inventory push package in the assembly. So a server can restore the chest but cannot take the item back out of the player.

The game ships a hash-validated, server-authoritative TransactionalInventory subsystem that would make this possible — InventoryManager.TransactionRequestServer applies a transaction then calls ValidateFinalHashes. It has zero consumers in the whole assembly. It is shipped, unwired infrastructure, and worth watching.

What is implementable is access control at open. TEFeatureAbs.CanLockOnServer returns true unconditionally and TEFeatureStorage does not override it; LockManager.LockRequestServer consults it per target and aborts the whole lock with "Target refused to be locked on server", so the loot window never opens. RoboticInbox already ships this technique. That gives a binary permission, not a directional one, so mailbox has to be redesigned:

  • Drop-only by proxy (recommended). Non-owners are refused the lock and get a deposit path the mod controls entirely — a chat command, or an interaction the mod fulfils server-side by moving items out of their bag. Server-authoritative, because the mod performs both halves.
  • Snapshot-and-restore at close. Snapshot on OnLockedServer, diff at OnUnlockedServer, restore if a non-owner removed anything. This broadcast does land, because the client clears SetUserAccessing(false) before requesting the unlock. But the duplication remains — the item is in their bag and unrecoverable. Ship only with an audit log, and never as a security boundary.

Feedback: use chat, never the sign

Both sign-as-output precedents destroy player text. RoboticInbox stashes the original in memory, overwrites the sign with a status message, and restores it 2–3 seconds later — but its restore removes the stash before validating anything and returns false on three paths without putting it back, and it writes the transient message with _syncData: true, so the status text is durable while the original lives only in process memory. A chunk unload or a crash inside that window destroys the player's sign permanently. RoboticSorter simply owns the sign and wipes it whenever slot 0 empties.

The sign cannot be both the input channel and the output channel. If the keyword lives on the sign, writing to that sign disables the box — briefly in the good case, permanently if the process dies mid-window. Use chat whispers (ServerTools already does, and it is the only per-player feedback in the corpus), plus a console command that lists the vocabulary, which falls out free from an enumerable registry.

Silent no-ops are the dominant usability trap and all three tools have them. An enumerable vocabulary lets you fix it cheaply: recognized-and-acted gets a whisper with counts; recognized-but-denied names the reason; an unknown #-token gets the nearest match by edit distance; and no # token stays silent, which is the overwhelmingly common case.

Defects in StrongBoxes as it stands

The mod is a stub, so these are not live bugs — but they are the specific things to fix, and several are the kind that would survive into a working implementation.

  • Null-chunk crash. World.GetChunkSync returns null for an unloaded neighbour — the normal answer, not an error — and SortBoxes.cs:50 short-circuits the LINQ chain with ?., so GetQualifiedSortTargets returns null and OnClose hands it to List.AddRange. The resulting exception inside a Harmony prefix leaves the player's lock state stale. ForceUnlockByChunk fires during POI reset — precisely when neighbours are absent.
  • No self-exclusion. IsQualifiedSortTarget tests distance only, so the sort box is its own candidate at distance 0. Under "already holds one" semantics it is its own perfect nearest match. It is the only one of the four tools with no self-exclusion.
  • No lootable filter. GetTileEntities().list returns every tile entity in the 256-tall column — doors, workstations, land claims, powered blocks. The README's claim that the scan "ranks the lootable ones by distance" is false on both counts.
  • Ordering. Each chunk's list is sorted in isolation and the nine runs are concatenated in HashSet order, so a container 12 blocks away can be processed before one 2 blocks away. The // TODO: Sort by distance marks the spot; the per-chunk sort is waste until it moves.
  • Unguarded GetAuthoredText().Text.ToLower() with no null check on either hop. ServerTools guards exactly this.
  • _unlockingPlayerId is discarded. Harmony would bind it for free. It is the only handle on the acting player, and every identity-based check depends on it.
  • Listener.Filter invoked without a null check while Callback is null-guarded — an asymmetry with no justification.

What this means for StrongBoxes

A layered permission model, ordered cheap-to-expensive, with the layers that must ship first marked. The ordering matters: each layer is only sound on top of the one before it.

LayerWhat it doesMVP?
L0 — Capture the actor Bind int _unlockingPlayerId in the patch; widen the listener contract to carry it. Resolve to PersistentPlayerData and PlatformUserIdentifierAbs; abort if either resolves null. Yes — everything else depends on it, and RegisterOnCloseListener is public, so widening it later breaks every registration site.
L1 — Qualify targets properly Self-exclusion, TEFeatureStorage + bPlayerStorage filter, then keyword exclusion, then in-use, then owner/ACL. Fix the null-chunk crash and the global sort first. Yes
L2 — Owner and ACL as the primary gate A target qualifies only if the actor is TileEntityComposite.Owner or IsUserAllowed(primaryId) returns true. Yes — this single layer answers all three lock-state questions correctly and uniformly. No reference tool implements it.
L3 — In-use guard IsLockedServer(feature, 0) on every target, re-checked immediately before each write. Skip busy targets; do not defer them. Yes — a data-integrity layer, not a courtesy.
L4 — Land claim Self as an alternative to owner/ACL, never a requirement, never Ally alone. Defer. Requiring it reproduces ServerTools' silent unclaimed-base failure.
L5 — Lock/password matching An extra grant path for a clan base whose members are in no ACL. Defer, probably never. Strictly weaker than L2 and imports the shared-password cross-talk.
L6 — #nosort opt-out A target-side property consulted during another box's scan. Yes — it is the only escape hatch when the other layers get something wrong, and retrofitting it means re-shaping the registry.

The shape of the implementation

  1. Keep the sort synchronous. Do not adopt RoboticInbox's coroutine. Synchronous work has no check-to-mutate window at all, so the entire class of torn reads and mid-scan destruction disappears by construction. The cost that forced RoboticInbox to yield does not exist here — a few dozen probes against 74,620. This is StrongBoxes' single largest correctness advantage and it should be defended, not traded for a bigger radius.
  2. Invert the loop from target-major to item-major before adding any ranking. The current shape can express distance ranking and nothing else; any predicate that depends on the item being placed is unreachable. All three references share this shape and none can choose a best target as a result. This is the one restructuring that cannot be retrofitted cheaply once the transfer body exists.
  3. Index targets by itemValue.type once per sort, after a global distance sort, so every candidate list arrives nearest-first for free. 44× fewer comparisons at realistic slot counts, behaviour-preserving.
  4. Top up existing stacks and place new ones. Top-up-only silently excludes every tool, weapon and armour piece.
  5. Never cache a TileEntity beyond the statement that uses it. Cache Vector3i; re-resolve at the point of use and compare identity before writing — which is vanilla's own discipline in XUiC_LootWindowGroup.OnClose.
  6. Couple MaxDistance to the chunk window in code, with a test asserting the ≤16 invariant. Today they are two unrelated constants in two files that happen to be compatible.
  7. Adopt the # sigil and a line-based matcher with one normalization boundary. It fixes the silent-disable class and makes StrongBoxes disjoint from ServerTools for free.
  8. Build the registry as a property store with triggers layered on, enumerable, refusing duplicate tokens.

Method, confidence and what was not checked

Two of the three references ship as DLLs only and were decompiled with ilspycmd against the game's own assemblies; ServerTools ships full source. All game-API claims were established by decompiling Assembly-CSharp.dll from packages/7dtd.assemblies.game/3.1.0.14 — the repo's declared dev version — rather than from memory or documentation. Decompiled third-party code stayed in .scratch/ and is not committed; it is licensed material.

Five deep readers covered the four codebases plus the game API, six topic writers synthesised the sections, and every candidate defect was handed to an adversarial verifier instructed to refute it and told the common ways such claims go wrong. 57 claims were tested: 22 fully confirmed, 35 partly true with the effect corrected downward, none refuted outright. The verifiers materially changed several conclusions — the Restack recursion is safe today rather than a stack-overflow risk, and the Turkish-I hazard applies to a future keyword rather than to sort.

What I checked and cleared

  • Shared-static corruption via ItemStack.Empty. Two mods pass it straight into UpdateSlot. Not a bug: Empty is a property returning a fresh instance, and UpdateSlot clones anyway. Two independent protections. (It does allocate on every call inside hot comparison loops — a minor garbage note, not a correctness one.)
  • A case-sensitivity asymmetry in ServerTools' sorter exclusion list. The comparison does mix a lowered left operand with a bare right one, but config lowercases both names at load, so the sorter itself is safe. The live instance of the bug is in Bank, not Sorter.
  • StrongBoxes' 3×3 window being too small for 15 m. It is not — guaranteed reach is 16 blocks. The finding is the uncoupled constants, not a present defect.

Limits

  • Nothing here was run in a live game. Every claim is static analysis plus the pure-logic harness; the measurements are of faithful ports of the scan geometries, not of the mods executing.
  • Claims are scoped to game tree V3.1.0-b14. Where a claim is version-sensitive I have said so — notably ItemClass.MaxCount, which exists on 3.1 and throws on 3.0.1.4, so prefer TryStackItem/CanStackPartly to encapsulate the stack cap.
  • The block census (6 signable of 1,563 storage blocks) came from a verifier resolving Extends inheritance; I did not independently re-run it.
  • The 50-character sign limit is declared on the shared editor textfield. Whether per-block LineCount/LineWidth clip a keyword-plus-label combination in practice was not verified in game.
  • The vocabulary work described here is not what #31 asks for. #31 is scoped to making the sort keyword functional and explicitly parks dump-to-nearest and overflow fallback. The registry, the sigil, #nosort and mailbox appear to be unticketed.

Questions this leaves you

  • Does #mailbox survive becoming an open-time permission? "Non-owners cannot open it at all, and deposit through a mod-controlled path" is a different product from "anyone can drop something in." If the deposit path must be a chat command, is that still the feature you want?
  • Should the source box also be owner-checked? ServerTools omits it, which lets a stranger's unlocked sort box be siphoned. Requiring it would break the plausible "shared community sort box" use case on Hades.
  • Where does keyword configuration live? StrongBoxes has no Config/ folder and no legal path to StrongUtils' ConfigManager — the repo has exactly one cross-project reference, and StrongCore does not exist yet.
  • Should #sort stay a trigger, or become a property consulted by a periodic sweep? A sweep would let sort boxes drain on a timer rather than only when a player touches them, and it shifts the registry's centre of gravity.

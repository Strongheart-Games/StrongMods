What a trader can offer, and what an admin can change

Vanilla builds a trader's quest list with seven offers per tier, a uniform draw over whatever rows quests.xml happens to declare, and no way at all to cap how far a quest sends a player. This is what the prototype changes, what it cannot, and what still has to be tested in game.

Where things stand

Built overnight, ready to read

Two Harmony patches replace the only two places the game makes these decisions, and two XML patches widen the dialog that shows the result. Settings live in one file beside the save. Every default reproduces vanilla exactly, so installing the prototype and changing nothing changes nothing.

Offer count

Seven per page was never seven in total

Vanilla builds up to seven quests for each tier from 1 up to the player's faction tier, and the dialog pages between tiers. A tier‑6 player already carries up to 42 offers; they just see seven at a time.

The finding that outranks the rest

A trader's tier‑6 pool is one quest

Read out of vanilla quests.xml

At tier 6 a trader has exactly one quest kind to draw from. A twelve‑offer page is twelve infested clears at twelve different POIs, and no weighting can change that — there is nothing to weight it against.

What follows from it:

  • Weights earn their keep at tiers 2 and 3, where six kinds compete for a slot.
  • avoid_offered earns its keep anywhere the page is bigger than the pool — which, above tier 3, is most settings.
  • Real variety at tiers 5 and 6 needs new quest content, not tuning. That is separate work.
  • max_tier is the blunt instrument that sidesteps it: cap pages at 3 or 4 and the mix stays varied.

Vanilla has the same problem at seven offers. Raising the count only makes it easier to see.

Distance

The largest real gain, and the trade it carries

Vanilla sorts every POI into three buckets by distance from the trader, prefers one, and walks the other two when the preferred bucket comes up empty. The preference is real; the boundary is not. That is why a trader in a thin region hands out two‑kilometre jobs, and why no XML anywhere can stop it.

What you gain

max="800" means no offer past 800 m. Full stop. The band edges become settings too, so a dense map can run tighter rings than a sparse one.

What it costs

On a sparse map a tight window means shorter pages, not further quests. A page that comes back with three offers instead of twelve is telling you the window is tighter than that trader's surroundings support.

Quest mix

Vanilla's mix is a row count, not a design

Selection is a uniform draw over whatever rows a trader's quest_list declares for that tier. Tier 3 offers clear‑type work about two‑thirds of the time purely because three of its six rows happen to be clear variants. Nobody chose that ratio. 

<types default_weight="1">
  <type match="*_clear"           weight="3" max="4" />
  <type match="*_clear_infested"  weight="2" max="2" />
  <type match="*_fetch"           weight="3" max="4" />
  <type match="*_restore_power"   weight="2" max="2" />
  <type match="*_buried_supplies" weight="1" max="2" />
</types>
  • match is a glob over the quest id, so quests added by other mods are covered as long as their ids follow a pattern you can name.
  • Anchored at both ends, which is what makes the table read the way it looks: *_clear matches tier3_clear and not tier3_clear_infested.
  • When two rows both match — tier2_fetch_clear matches *_clear and *_fetch_clear — the longer pattern wins, so where a row sits in the file never changes the result.
  • max caps a kind per page, so no single type takes over even when the dice like it. Vanilla has the same field on every quest and ships it disabled everywhere.

Ruled out

Three routes that look easier than they are

Patching GetQuestList

Where the old stub sat. It is a cache read — the list is already built by the time it runs. The real seam is PopulateActiveQuests.

One flat page for every tier

The game supports a tier‑less quest row, so this looked free. Accepting a quest sends (tier, index‑within‑tier) to the server, so a flat index removes the wrong quest from the list.

64 quests on one screen

The UI canvas is 1080 px tall and a response row is 40. Twenty‑four rows fit at a readable size; three go to navigation. Getting past 21 needs a multi‑column grid or per‑tier sub‑pages.

Sub‑pages are the tempting one, and they need no code. The catch: the “more jobs” link cannot be hidden when there is nothing behind it, because the game has no dialog requirement that tests how many quests a tier holds. Every trader would carry a permanent dead row. Both routes are written up in Docs/configuration.md; neither is shipped.

The bill

What this approach costs

The mod now owns a copy of a game algorithm. Both replaced methods are rewritten outright, so a game update that changes how offers are built will not surface as a compile error.

Two things limit the damage. The replacement keeps vanilla's observable contract — same tier loop, same used‑POI bookkeeping, same special‑quest pass, same final sort — so divergence stays visible as a diff against the research note. And the repo's smoke suite resolves both patch targets against every declared game version, so a renamed or re‑signatured method fails the build instead of failing quietly at runtime.

Evidence

What is verified, and what is not

Verified off‑game

  • Project builds clean.
  • 269 of 269 repo tests pass — including both new Harmony targets resolving against V3.1.0-b14 and V3.0.1-b4.
  • Both XML patches replay against both vanilla trees with no warnings. The game logs “did not apply” for a patch element matching nothing and the suite fails on it, so all 84 dialog inserts and 4 UI attribute writes really matched.
  • 33 checks over the selection logic: globbing, longest‑pattern‑wins, clamping, the band schedule, a 3:1 weight ratio over 40,000 draws, per‑type caps, exhaustion, repeat avoidance.

Needs an in‑game pass

  • That a trader renders more than 10 rows, and that a 1006 px window sits sensibly on screen. The anchor arithmetic was read out of the game's code, not observed.
  • That clicking row 9 accepts quest 9. The removal path is per‑tier and should hold, but it is untested.
  • That the settings file is written to the save folder on first run and read back on the next.
  • That a distance window finds anything on a real map, and how short pages get when it does not.

Over to you

Three decisions worth making before tuning

  • The tier‑6 pool. Accept twelve identical infested clears, cap pages with max_tier, or treat new late‑tier quest content as its own piece of work.
  • The display ceiling. 21 rows per page is what fits today. Going higher means a multi‑column dialog, and that is a design call, not a code one.
  • Owning the algorithm. The rewrite is what #33 needs, but it is a standing maintenance commitment on every game update. Worth confirming that is the trade you want.

Deploy-shape harness: what a redirected deploy proves

A prototype file-based harness (StrongDev/.ai/tools/deployshape.cs) now drives real -t:Deploy builds of disposable probe projects into .scratch/deploy-shape/ roots and asserts the outcomes. Result: 21 assertions pass, 0 fail — the overlay guards from the 2026-07-30 incident hold, the #37 version check both skips and refuses exactly as designed — and one genuine gap surfaced: the mirror misses source deletions on plain incremental deploys, because staging (bin\) is maintained additively.

What was attempted

Issue #42's uncovered piece is the deploy shape: nothing automated exercises -t:Deploy and checks what lands. This effort prototyped the harness as a C# file-based app per the #36 rule, following the loclint.cs precedent (top-level program, --selftest mode, run via dotnet run).

The mechanism: synthesized probes, real build logic

Stale-deletion and destructive scenarios must never touch tracked project sources. The task suggested copying a small modlet under .scratch/deploy-shape/src/ — but a copied csproj's relative ..\build imports would not resolve from there, and rewriting the copy's import line is the same act as generating the project outright, with less control. So the harness synthesizes minimal probe projects whose csprojs import the repo's real build/Modlet.targets (or Overlay.props + Overlay.targets) by absolute path, computed at run time from the repo root. This works because every tracked entry point resolves its own siblings via $(MSBuildThisFileDirectory) — the importing project's location is irrelevant. The logic under test is byte-for-byte what tracked projects run; only the content is disposable.

Every build runs with its working directory at the repo root, so relative -p:ModsDir values anchor at $(MSBuildStartupDirectory) exactly as build/Deploy.targets documents (#46/#52). No full-solution build was run (parallel efforts in flight), no real install was touched, and the Tests/ project was not modified. Each build's full log is kept under .scratch/deploy-shape/logs/.

dotnet run StrongDev/.ai/tools/deployshape.cs -- --selftest   # 9 internal cases, all pass
dotnet run StrongDev/.ai/tools/deployshape.cs                 # full run: 21 pass, 0 fail, 1 observation

Probe projects: MirrorProbeModlet (modlet, ModLoadTier=AfterDependencies, two Config files), OverlayProbeScoped (overlay, MirrorOnDeploy Include="Config"), OverlayProbePlain/OverlayProbeEmpty (overlays with no MirrorOnDeploy — the empty-vector shape), and RefusalProbeModlet (deployed at a fake install planted in scratch).

Findings

Finding 1 · real gap · staging staleness defeats the mirror on incremental deploys

The documented contract — "source is authoritative for content AND existence, so a file removed from source stops existing … at the next deploy" (build/Deploy.targets lines 10–12; same claim in AGENTS.md) — does not hold for a plain incremental dotnet build -t:Deploy. The mirror runs staging→destination, but staging itself is maintained additively: Modlet.targets' Build target (lines 30–36) copies Content into bin\ and never removes what is no longer Content. The stale file rides staging into every subsequent deploy.

source
Config/stale.xml deleted
Build: additive copy──▶stale file NOT removed
bin\Debug staging
stale.xml lingers
Deploy: faithful mirror──▶mirrors staging exactly
destination
stale.xml still deployed

Evidence: S2a — after deleting Config/stale.xml from the probe source, a plain -t:Deploy exits 0 with the file still present at the destination and in staging, and zero removed stale announcements (logs/s2a-redeploy.log). After -t:Clean;Deploy the deletion happens and is announced (S2b). Scope of the claim: verified on the modlet path only. The code-mod path (Mod.targets, SDK OutDir) was not run, but its staging is also maintained additively by the SDK's copy targets, so the same shape is plausible there — unverified. Proposed ticket below.

Finding 2 · guard confirmed · the 2026-07-30 empty-vector incident cannot recur today

With no MirrorOnDeploy declared (the exact shape that once turned the whole deploy root mirror-scoped and deleted unmanaged files), the redeploy deleted nothing: planted files at the deploy root, inside Config/, and in a nested directory all survived (3/3), with no stale-removal announced. The load-bearing guards are the Condition="'@(_MirrorDir)' != ''" / '@(_MirrorFileId)' != ''" clauses on every batched include in build/Overlay.targets (lines 148–166). This was previously only protected by a comment saying "do not simplify these away" — it now has an executable regression test.

Finding 3 · #37 check · both branches proven without touching a real install

The skip branch: a redirected destination with no game assembly above it (roots/*/Mods) is not an install and is not checked — every scenario deployed cleanly with no refusal text. The refusal branch: planting a garbage Assembly-CSharp.dll at .scratch/deploy-shape/roots/fakeinstall/7DaysToDie_Data/Managed/ makes _VerifyInstallVersion classify the destination as a game install, hash the assembly against both declared package trees under packages/, match neither, and refuse with the full instructional error (quoted in the results table) — exit 1, nothing deployed. This technique needs only the restored packages tree, which CI already has, so the refusal path is CI-assertable; no licensed install is involved at any point.

Decisions and trade-offs

  • Synthesized probes over a copied real modlet. A copy's ..\build imports don't resolve from .scratch/; pointing them home means editing the copy anyway. Synthesis gives complete content control (needed for plant/delete/backdate steps) while the imported build logic stays the tracked files themselves. Trade-off: probe content is minimal, so arrival assertions are shape-level — the harness does not prove any real mod's content survives its own deploy (the solution-sweep lane below covers that).
  • Absolute import paths, written at run time. Makes the probes machine-specific throwaways — exactly right for .scratch/, never committable. The alternative (passing the build dir as a -p: property into a property-referencing import) works too but adds a moving part to every invocation.
  • S2's stale-deletion assertion uses -t:Clean;Deploy, matching the documented intent, while the plain-incremental behavior is recorded as an observation rather than silently worked around — the discrepancy is finding 1, not a harness bug to paper over.
  • The refusal path was demonstrated, not just described. The task allowed stating how; a fake install inside .scratch/ proves it with zero risk to real installs, so the harness does that.
  • Timestamp control for the protective tests: destination edits get mtime=now (survival case); the overwrite case backdates the destination 2h and touches the source to now. Deterministic regardless of copy-time mtime preservation.
  • No full-solution deploy sweep in this session — solution builds were off-limits with parallel efforts running. The per-mod sweep (every deployable mod lands its DLL/ModInfo/Config; IsDeployable=false projects land nothing) is specified for CI below but not executed here.

Recommended CI shape for #42

Two complementary lanes, both pure scratch-redirect, no artifact upload:

  1. Semantics lane (this harness). Promote deployshape.cs from StrongDev/.ai/tools/ to build/tools/ (the durable-tool home per #36) and add a workflow step: dotnet run build/tools/deployshape.cs — its exit code already gates (1 on any failed assertion). It covers mirror arrival + stale deletion, tier prefixes, protective-additive survival, scoped mirroring, the empty-vector guard, and both #37 branches. Runtime cost observed locally: ~10 short modlet/overlay builds, well under a minute after restore. Optional extension: plant a 7DaysToDieServer_Data fake to assert #37's unit-follows-destination rule.
  2. Sweep lane (not yet built). One solution-wide redirected deploy — dotnet build StrongMods.sln -t:Deploy -p:ModsDir=<scratch> -p:SdtdSavesDir=<scratch2> — then assert per project: deployable mods produce a folder with DLL (code mods), ModInfo.xml, and Config/; folder names carry the declared tier prefix; IsDeployable=false projects and templates produce nothing. This is cheap to express as a second mode of the same tool (--sweep <root>) reading each csproj's declared tier.

Both lanes keep the standing rule intact: workflows never run -t:Deploy without a scratch redirect, and the harness hard-codes redirect-only invocation.

What remains

  • The sweep lane (solution-wide redirected deploy + per-mod assertions) — specified above, not implemented.
  • Code-mod deploy path unverified. All probes were modlets/overlays (no compile step keeps the harness fast and game-tree-independent). A code-mod probe would verify the Mod.targets + OutDir staging chain, including whether finding 1 reproduces there.
  • The saves-root overlay shape (DeployRoot=$(SdtdSavesDir), -p:SdtdSavesDir redirect, StrongholdSaves' file-scoped mirror) — semantics are the same Overlay.targets code proven here, but that specific root wiring was not exercised.
  • Directory-demotion edge, untested: if a directory named in MirrorOnDeploy is deleted from staging entirely, the Directory.Exists partition in Overlay.targets (line 145) demotes the declaration to a file identity — what happens to the destination directory's contents was not probed. Worth one more scenario before CI adoption.
  • Promotion + workflow wiring is human-review work: moving the tool to build/tools/, adding the workflow step, and deciding whether the sweep lane lands in the same file.
  • The disposable probe sources, roots, and logs were not retained. This report preserves the conclusions; #107 carries the durable verification work.
